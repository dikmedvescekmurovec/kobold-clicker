# Incremendal Side Scroller

Godot 4.7 (GDScript) incremental game. Current work: a clickable, procedurally generated hex map drawn with AI-generated pixel-art sprites.

## Map code (`Scenes/Map/`)
| File | Contents |
|---|---|
| `hex_grid.gd` (`HexGrid`) | Pointy-top offset grid with odd rows shifted right (same as the TileMapLayers). `Edge` enum (E, SE, SW, W, NW, NE) and `EDGES`, `neighbor`, `neighbors`, `opposite`, `distance`, `corners`, and the edge bitmask pair `edge_mask` / `mask_edges` that roads are described with |
| `sheet_meta.gd` (`SheetMeta`) | Reads `AI-sprites/spritesheet/hex_tileset.json` once per run and hands out its `meta` block, so nothing restates the rules the sprites were drawn to. `env_adjacency()` is the adjacency table, with each environment's self-entry stripped |
| `hex_tileset.gd` (`HexTileset`) | Builds the TileSet at runtime from `AI-sprites/spritesheet/hex_tileset.json` (56×64 tiles). `atlas_coords`, `road_name`, `blend_name`, `env_rank`, `can_border`, `opaque_mask` |
| `hex_map.tscn` / `hex_map.gd` (`HexMap`) | GroundLayer, one `Blend_<env>` layer per spreading environment (created in `_ready`), RoadLayer, Highlight. `set_ground` redraws the blends of the cell and its neighbors, reading the environment of cells that aren't drawn yet through the `hidden_env` Callable, so a tile looks the same however late it is discovered. `get_tile_info` includes `blends` and `environments` (visible pixel share per environment). Owns the `fog` overlay and the `player` token. Signals `tile_hovered`, `tile_clicked`, and `dragged` (mouse movement while dragging, for the owner of the camera). A click selects a tile; a press that travels more than `DRAG_THRESHOLD` pans instead. `set_player_cell` moves the player token |
| `player_token.gd` (`PlayerToken`) | The player's character, an `AnimatedSprite2D` with an "idle" and a "run" animation from `Assets/Player`. The sheets' frames are wide (room for the attack swing), so one `BOUNDS` crop, the union over both sheets, cuts every frame down to the character; sharing it keeps the character still when the animation changes. Drawn at `SCALE` (half size). `walk(path)` runs it from tile to tile at `SECONDS_PER_TILE`, `advance(delta)` steps that on (tests drive it directly), `finish_walk()` jumps to the end, and `arrived` fires on the last tile. `HexMap` creates it in code, after the highlight, so it draws on top |
| `fog_overlay.gd` (`FogOverlay`) | The translucent grey hex drawn over every tile that is seen but not discovered. `HexMap` creates it in code, between the roads and the outlines |
| `hex_highlight.gd` | Hover and selection outlines: a bright band with a dark ink border, readable on every terrain |
| `environment_generator.gd` (`EnvironmentGenerator`) | Random-frontier growth under `ALLOWED`: prefers neighbors, boosts regions under `MIN_REGION_SIZE`, damps regions over `MAX_REGION_SIZE`, then merges small regions. `extend()` grows an existing map into new cells without touching the old ones (they are frozen against merging), which is how the map enlarges. Tunables are at the top |
| `town_world.gd` (`TownWorld`) | 256×256 world of towns (small 1%, medium 0.5%, fortress 0.1%, never on neighboring spots). Each town links to its 1/2/4 nearest towns (small/medium/fortress) within 20 steps, in both directions |
| `road_network.gd` (`RoadNetwork`) | Routes roads along the town links with A*, using only shapes the sprites have (straight, 120° curve, 3/4/6-way). Roads stop at town edges and never cross a town tile. Terrain-independent, so a world always gives the same roads. `extend()` adds the links a window brings into reach, routing each inside its own box (around its two towns), so a road never moves once laid — growing the map only ever adds edges, sometimes turning a drawn road into a junction |
| `map_builder.gd` (`MapBuilder`) | Generates the map (`START_RECT`: 20×11 cells around cell (0, 0), which the camera centers on screen) and draws it as the player uncovers it. `rect` is what the map covers now: coming within `EXPAND_MARGIN` of an edge grows it by `EXPAND_BY` on that side (`expand_if_needed`, on arrival), generating the new land, its tiles and the roads it brings into reach, and redrawing the blends and roads of drawn tiles the new land touches. Everything already generated stays exactly as it is. Every cell is in one `State`: `HIDDEN` (the fog of war, nothing drawn), `UNDISCOVERED` (drawn under the grey fog, can't be walked to) or `DISCOVERED`. `create()` generates everything and draws `start_cells()`: the discovered center, where the player starts, ringed by six undiscovered tiles. `discover(cell)` takes the grey off a tile next to the player (`can_discover`), draws the tiles behind it as undiscovered, and sends the player walking onto it. `move_to(cell)` sends the player walking to a discovered tile over `route_to(cell)`, a shortest path of discovered tiles (`can_move_to` refuses anything else, and anything at all while `walking`); arriving emits `arrived(cell)` and discovers nothing by itself. `reveal_all()` discovers the lot. `origin` is the world spot at cell (0, 0): generated environments, plus that environment's town sprite where the world has a town. Before drawing, it clears any town within `START_TOWN_DISTANCE` (5) of the center and guarantees a small town exactly that far out, which a road links to cell (0, 0); that town's world spot is `start_town`. `_spot(cell)` is the crossing from map cells to world spots |

`Scenes/main_scene.gd` has the exported `world_seed` and `map_seed` (0 = random; the used seeds are printed), `map_origin`, `zoom` (3 by default, whole numbers only so sprite pixels stay square) and `ui_scale` (2). It prints the clicked tile's environment weights and town connections, and builds the UI in code, so the scene file stays untouched while the editor has it open: a side panel flush against the right edge, running the full window height and hidden until a tile is selected — a green title bar with the title and an X at its right end, over a cream body holding one row per environment on the tile (a 16 px swatch cut from that environment's own hex-sheet tile, plus its percentage), a "Discover" and a "Move here" button pinned to the bottom — discovering the tile next to you walks you onto it, and "Move here" goes back to any tile already discovered (the camera follows until the player arrives), and an X top-right that closes the panel and calls `HexMap.deselect()`. Opposite it, an "Items" button in the top-left corner opens the bag: the same titled panel against the left edge, holding every item the world has handed over as a grid of tan squares straight on the cream body — the pack puts nothing between the two, so neither does this — newest first, each ringed in its rarity's colour above common. Clicking a square puts that item's stat block in the grid's place — name and rarity in that rarity's colour, what the piece is worth, then what it rolled — with a Back button. The squares on the panel at the end of a fight open the same way, in the verdict's place. The grid scrolls by wheel and by dragging it, and never shows a scrollbar; a press that travels is a drag and one that does not is a click, the same rule `HexMap` uses to tell a pan from a tile click. The button and the panel both go while a fight is on — a `Control` left in that corner would take the mouse before the fight saw it and quietly eat the player's swings. `inventory_path` is exported beside the seeds so tests can point it away from the real save.

## Combat code (`Scenes/Combat/`, `Scenes/Enemies/`)
A tile has to be taken before it can be discovered: ten enemies in 60 seconds, one click per point of damage. Winning calls `MapBuilder.discover` exactly as pressing Discover used to; losing changes nothing and can be retried at once.

| File | Contents |
|---|---|
| `enemy_roster.gd` (`EnemyRoster`) | Every enemy under `Assets/Enemies`: its `Tier` (COMMON/ELITE/BOSS), its `Size`, its `Facing` (the packs disagree; `CombatActor` mirrors only the ones drawn facing right, so nobody walks in backwards), the environments it lives on, and its sheet per animation. Health is not written per enemy — `SIZE_HP` and `TIER_HP` multiply into `hp_modifier`, so the whole curve is tuned from two tables. `weight` is written per entry, because being numerous has little to do with being big: whole numbers on one absolute scale, commons 30-100, elites 8-20, bosses 1-4, bands that never overlap. `pick` draws weighted by it, and a slime at 100 is the commonest thing on every terrain. `frame` and `bounds` are measured, not guessed (see the gotcha below) |
| `encounter.gd` (`Encounter`) | The rules, with no nodes: `for_tile(cell, env)` rolls nine commons and an elite, seeded from the cell so a tile always fields the same fight. Bosses are never rolled here. `hit()` takes a point off, `advance(delta)` runs the clock through the walk-ins and deaths, `won`/`lost` end it. Health is `hp_modifier` over a base that grows with the distance from cell (0, 0) |
| `combat_actor.gd` (`CombatActor`) | An `AnimatedSprite2D` built from a sheet at runtime, as `PlayerToken` is. Serves both sides. Scaled and stood up by its *idle* frames, so `position` is the middle of its feet whatever the attack or death frames sprawl into |
| `combat_scene.tscn` / `combat_scene.gd` (`CombatScene`) | The view: backdrop, the two fighters, the HUD, the clicks, the verdict. A `CanvasLayer` the main scene adds in front of the map rather than a scene change — the map holds a whole generated world in memory that a scene change would throw away, so it is hidden and its `process_mode` disabled instead. Drawn height comes from `SIZE_HEIGHT`, so a slime is knee-high and a boss looms |

## Items (`Scenes/Items/`)
Every enemy killed rolls for gear, and what drops is the player's whatever the fight does next — a lost fight still leaves the kills that were made. A drop is its own thing: it rolls a rarity off the enemy that carried it and modifiers off that rarity's band, so two Wooden Swords are two different swords and nothing stacks. **Nothing reads any of it for gameplay yet** — a click still does one point of damage. The stats and modifiers are rolled, saved and shown, and the chunk that makes a click do `damage` will be the one to retune every number in these tables.

| File | Contents |
|---|---|
| `loot_table.gd` (`LootTable`) | The seven pieces of gear under `Assets/Gear` — sword, shield, armour, boot, torch (offhand), ring, amulet: their icons, their relative weights, and two stat lists apiece. `stats` is what the piece *is*, the few numbers it shows and the only ones a PERCENT modifier can scale; `affixes` is what it can *carry*, stats it has none of and still rolls a flat modifier for, which is how a ring with no health rolls "+8 Health" (`has_stat` / `affixes_of` / `can_roll`). Stats span pieces on Path of Exile's rule: offence on the weapon, health/armour/resistances nearly everywhere, and only `damage` (sword), `move_speed` (boot) and `block_chance` (shield, torch) locked to one place — `test_inventory._test_slot_locks` pins those three. And how often anything drops at all. As with health, the chance is not written per enemy: `TIER_CHANCE` and `SIZE_CHANCE` multiply into `chance_for`, capped at 1. `roll(enemy, rng, guaranteed)` gives `null` or a whole `Item`, drawing the chance first so a kill that leaves nothing still costs exactly one draw. A fight of nine commons and an elite is worth about a third of an item, which `test_inventory.gd` holds to. `STAT_LABELS` and `stat_line` are the one place a stat is spelled |
| `item_rarity.gd` (`ItemRarity`) | The five steps (common, uncommon, rare, elite, unique), what each enemy tier is worth as integer weights out of a thousand, how many modifiers each step carries, the two colour ramps and the `StyleBoxFlat` an item square is drawn with. Kept apart from `Item` because a `const` in one class naming another class's enum is where Godot's cycle checker bites: `Item` reads these tables, so these tables never mention `Item`. UNIQUE is hand-crafted, weighted zero everywhere and cannot drop — a test holds that until the chunk that writes them |
| `modifier_table.gd` (`ModifierTable`) | The pool, and three ways onto a piece: a `PERCENT` modifier scales a stat the item has (`has_stat`), a `FLAT` one adds a stat the item is merely allowed to carry (`can_roll`, so base stats *or* affixes), and a `PLAYER` one buffs the player and fits anything. The resistances, the attributes, leech and life-on-hit are flat-only — each is a quantity you add up across the set, so "+35% Fire Resistance" is the whole idea and a percentage of it would mean nothing; that is also what lets them sit in `affixes` on pieces showing none of them. `pool_for` builds the candidates first, so a modifier an item cannot carry is never drawn rather than rolled and rejected, and `roll` draws without replacement so nothing repeats on one piece |
| `item.gd` (`Item`) | One dropped thing: type, rarity, rolled modifiers, and the lines the stat block shows. Only those three are stored — base stats are looked up from `LootTable` every time, so retuning a sword retunes every sword already held. `to_dict`/`from_dict` are the save, with the rarity written by name because an enum value is only a position |
| `inventory.gd` (`Inventory`) | `items: Array[Item]`, plus `first_elite_taken`, and the JSON under `user://inventory.json`. It never saves itself: the main scene owns it and decides when, and the path is a parameter so the tests and the screenshot scripts never touch the player's own save. Loading survives a missing, unreadable or corrupt file, refuses a save from a newer build rather than guessing at it, and migrates the version 1 tally of names into plain common items |

## UI code (`Scenes/UI/`)
| File | Contents |
|---|---|
| `palette.gd` (`Palette`) | The few colours the game draws with in code rather than through a sprite. `INK`, `BONE`, `GOLD`, `EARTH_DK`, `SLATE` and the rarity ramp are `hexlib.py` hexes, so an outline matches the generated art it sits on; `PANEL_CREAM`, `SLOT_TAN` and `SLOT_TAN_DK` are the UI pack's, so a slot matches the panel art it sits on |
| `item_details.gd` (`ItemDetails`) | What one item is, written into a `VBoxContainer`: its name and rarity in that rarity's colour, its base stats, then its modifiers. The bag and the fight's panel both fill from here, so an item reads the same in both. Wants a bone background — the darker half of the rarity ramp was picked to be read on the white panel, not on wood |
| `item_slot.gd` (`ItemSlot`) | One item as a square: its icon on a flat tan socket, ringed in its rarity's colour above common. The UI pack draws an inventory slot as exactly that — one flat square with a gutter around it and nothing else — so the `StyleBoxFlat` is the art rather than a stand-in for it, and it draws the rarity ring in the same call. `main_scene.SLOT_GAP` keeps the pack's seven-to-one square-to-gutter proportion. Both places that show an item use it — the bag's grid and the panel at the end of a fight — so a rare piece looks the same in each |
| `ui_theme.gd` (`UITheme`) | Builds the `Theme` at runtime from `Assets/UI/ui_sheet.json`, the way `HexTileset` builds the TileSet. Each sprite becomes an `AtlasTexture` in a `StyleBoxTexture` with **that sprite's own** nine-slice margin, read from the JSON, and tiled (never stretched) axes — a panel's frame and a button's bevel are not the same thickness. One `FONT_COLOR` and one `DISABLED_FONT_COLOR` cover every button, because every face is now the same green replayed in another key. `UITheme.theme()` returns the shared theme; use it through the type variations `WoodPanel`, `TextPanel`, `HeaderBar`, `PanelLabel`, `WoodButton`, `WoodDangerButton`, `LightButton`, `LightDangerButton` and `CloseButton`. `CloseButton` is the odd one: an icon rather than a stretched face, so it has no texture or content margin and no pressed sink (the sprite holds it), and `UITheme.icon_size` says how big to make it — a Button with no text and no padding has no minimum size of its own |

Set `theme_type_variation` on a plain `Button` and Godot drives hover, press and disable itself; `wood` buttons are meant to stand on `WoodPanel`, `light` buttons on `TextPanel`. The main scene scales its panel by `ui_scale`, so UI pixels are a whole multiple of the screen pixel like the map's.

## Sprites
The sprites are generated by `AI-sprites-generator/` (Python, exported through Aseprite). Its README holds the palette, geometry, adjacency table and blend rules. `AI-sprites/` is build output: change the generator, preview with `qa.py` and get the user's approval, then run `build.py`.
The six per-environment slimes are generated too: `slimes.py` swaps the blue slime pack's body ramp for each environment's `hexlib.PALETTE` ramp, `qa.py slimes <tag>` previews and checks them, and `build_slimes.py` writes them to `Assets/Enemies/<Env> Slime/`. They skip Aseprite and the atlas -- the source is already a PNG pack and they ship as ordinary RGBA sprites under `Assets/`.
**The interface is not generated.** It is cut from the bought Craftpix pack under `Assets/Potential/2D Pixel UI/` by `tools/ui_kit.py`, which writes `Assets/UI/` (the sheet, the loose sprites and `ui_sheet.json`) and a tiling preview at `tools/qa/ui_kit_tiling.png`. The pack ships finished panels and buttons rather than a slice kit, so that file is where it is written down which rectangle of which pack sheet is which sprite and where its nine-slice margins fall. Both panels are the pack's own art, cut whole; the one thing that is not is the button, because the pack has one colour and three states — the danger and disabled faces are palette swaps of the green, mapped by hue and saturation with each step's lightness kept, the way `slimes.py` recolours the blue slime.

The same file also cuts the **gear icons** (`GEAR`, `gear()`), because it is where it is written down which rectangle of which bought sheet is which sprite and a second script saying that a second way is how the two drift apart. They are not theme sprites: they go to `Assets/Gear/` as loose 32×32 PNGs for `LootTable.ROOT` to load by path, never into `ui_sheet.png` or `ui_sheet.json`, and they skip `check()` for the reason the close button does — an icon is drawn, never stretched, so it has no nine-slice to hold flat. The preview is `tools/qa/ui_kit_gear.png`, every gear icon the game has on the bag's tan socket, because the one thing that can go wrong is whether the new ones look pasted in beside the old. Ring and amulet come off `Icons.png` (a 6-column grid on a 16 px pitch, rows *not* evenly spaced — each entry's y and height are that one icon's measured extent), doubled to land near the size of the RPG pack's 28 px art, which doubles their pixel too; that is why only the two pieces no pack draws are taken from it, and the torch is the RPG pack's own.

`Main_tiles.png` is laid out as a family: four colourways (a brown or green header over a cream or a brown body) by three frame weights, plus header-less bodies, a big cream panel, scrollbar rails and thumbs, close buttons and slot tiles. The game takes the header-less brown body, the big cream panel, and the green title bar **cut off its panel rather than taken with it** — the pack draws bar and body as one sprite, which fixes the bar at 13 px, and Pixellari needs 16 to stay legible. Cut on its own the bar is a nine-slice like any other and grows to whatever the title needs, with the body panel stacked under it. That is what `main_scene._titled_panel` builds, and `_body_of` hands back the VBox to fill.

The close button is the pack's own drawn X, not the letter typed on a green button: one 9×10 icon the pack uses on every panel size, tinted to the surface it sits on, so the green one is cut for the green bar. The pack draws it once, so the other three states come from the pack's own rules — pressed is the face a pixel lower with its drop shadow gone, which is how the pack presses every button it has, and hover lifts the frame's lightness by the step measured off the pack's green face (#50a978 → #68c97e, the same lift that takes its shade #478773 to #50a978).

The earlier AI-generated UI sheet (`ui.py`, `build_ui.py`, `qa.py ui <tag>` and `AI-sprites/ui/`) is no longer wired to anything.
Both builds share `buildlib.py`: the Aseprite call, the pass that reads every exported PNG back and compares it to the source pixels, and the report. Which environments each road material is used on lives in `roads.py` (`MATERIAL_ENVS`), and is what ships to the engine as JSON meta `road_materials`.

## Rules and gotchas
- **Rules come from the JSON meta:** `blend_rule`, `blend_priority` and `env_adjacency`, all read through `SheetMeta` — `HexTileset.can_border` and `EnvironmentGenerator.allowed()` are the same table, so the generator cannot produce a border the sprites can't draw.
- **Map origins must be on even rows**, otherwise world neighbors don't match on-screen neighbors (`MapBuilder` asserts this).
- **Test pattern:** everything in `tests/` extends `tests/harness.gd`, which starts `_run` deferred and holds `_check`, the failure count, `_report("suite name")` and the shared `WORLD_SEED`. Each `_test_*` function returns `true` and `_run` checks that it did, so a script error counts as a failure.
- **Editor conflicts:** the Godot editor is often open. After changing `project.godot` or `.tscn` files outside it, reload the project so the editor doesn't overwrite them.
- **A nine-slice margin is only correct if what it leaves over is flat:** a `StyleBoxTexture` repeats the centre and the four edge cells, so every row the top and bottom bands tile horizontally, and every column the side bands tile vertically, has to be one colour or the seams show. `tools/ui_kit.py check()` re-reads each sprite and refuses to export one that is not — which is how the button margins were found (bottom 3 looked right and put one pixel of the corner bevel into a tiled column).
- **Pixellari renders cleanly only at 16 px**, its native size; below about 14 the glyphs break up. To make the interface smaller, lower `ui_scale` rather than the theme's `FONT_SIZE`.
- **Enemy sheet geometry is measured, not guessed:** frame widths run 32 to 245 px with no relation to the sheet height, and a greatest-common-divisor guess gets Dwarf Warrior and Mimic wrong. The frame width is the smallest divisor of every sheet width in the pack where each frame boundary lands on a fully transparent column; `test_enemies.gd` re-checks that against the sprites, so adding an enemy means measuring it the same way.
- **Recolours never redraw:** an environment slime is a pixel-for-pixel palette swap of the baseline, so its silhouette and animation are the baseline's and `EnemyRoster` can share one `frame` and one `bounds` across all six. `qa.py slimes` fails on a single changed alpha pixel.
- **Loot belongs to the attempt, not the tile:** a tile's ten enemies are seeded from its cell, so the same tile always fields the same fight, but `Encounter.loot_rng` is left unseeded (a `RandomNumberGenerator` seeds itself, so there is no `randomize()` to add) and re-fighting a tile can turn up something else. Tests set the seed themselves.
- **What an item shows and what it can roll are two different lists:** `stats` is the piece's own and `affixes` is only a permission — `affixes_of` never reaches a stat block, so adding a stat there widens the modifier pool without lengthening what the player reads. The two must not overlap, and an affix with no `FLAT` modifier naming it is unreachable; `test_inventory._test_items` fails on both.
- **Every modifier value is a whole number:** it means one `randi_range` a modifier, it means the save holds `14` rather than `14.0`, and it means a round-tripped item can be compared with `==` instead of an epsilon. Base stats may hold a float (`attack_speed`) precisely because they live in a const table and never cross the file.
- **A square in the bag takes no mouse input at all** (`MOUSE_FILTER_IGNORE`): the grid sits in a `ScrollContainer` that has to see every press to tell a drag from a click, and a square that swallowed the press would break every drag that started on one — which is most of them. Which square was clicked is worked out from where the cursor is.
- **A lambda captures by value, and so is a `PackedStringArray`:** anything a test gathers from a signal has to be collected in an `Array`, which is shared, or the count outside the lambda never moves.
- **Commit** `.uid` and `.import` files.
