# Incremendal Side Scroller

Godot 4.7 (GDScript) incremental game. Current work: a clickable, procedurally generated hex map drawn with AI-generated pixel-art sprites.

## Map code (`Scenes/Map/`)
| File | Contents |
|---|---|
| `hex_grid.gd` (`HexGrid`) | Pointy-top offset grid with odd rows shifted right (same as the TileMapLayers). `Edge` enum (E, SE, SW, W, NW, NE) and `EDGES`, `neighbor`, `neighbors`, `opposite`, `distance`, `corners`, and the edge bitmask pair `edge_mask` / `mask_edges` that roads are described with |
| `sheet_meta.gd` (`SheetMeta`) | Reads `AI-sprites/spritesheet/hex_tileset.json` once per run and hands out its `meta` block, so nothing restates the rules the sprites were drawn to. `env_adjacency()` is the adjacency table, with each environment's self-entry stripped |
| `hex_tileset.gd` (`HexTileset`) | Builds the TileSet at runtime from `AI-sprites/spritesheet/hex_tileset.json` (56×64 tiles). `atlas_coords`, `road_name`, `blend_name`, `env_rank`, `can_border`, `opaque_mask` |
| `hex_map.tscn` / `hex_map.gd` (`HexMap`) | GroundLayer, one `Blend_<env>` layer per spreading environment (created in `_ready`), RoadLayer, Highlight. `set_ground` redraws the blends of the cell and its neighbors, reading the environment of cells that aren't drawn yet through the `hidden_env` Callable, so a tile looks the same however late it is discovered. `get_tile_info` includes `blends` and `environments` (visible pixel share per environment). Owns the `fog` overlay and the `player` token. Signals `tile_hovered`, `tile_clicked`, and `dragged` (mouse movement while dragging, for the owner of the camera). A click selects a tile; a press that travels more than `DRAG_THRESHOLD` pans instead. `set_player_cell` moves the player token |
| `player_token.gd` (`PlayerToken`) | The player's character, an `AnimatedSprite2D` with an "idle" and a "run" animation from `Assets/Player`. The sheets' frames are wide (room for the attack swing), so one `BOUNDS` crop, the union over both sheets, cuts every frame down to the character; sharing it keeps the character still when the animation changes. Drawn at `SCALE` (half size). `walk(path)` runs it from tile to tile at `SECONDS_PER_TILE`, `advance(delta)` steps that on (tests drive it directly), `finish_walk()` jumps to the end, and `arrived` fires on the last tile. `HexMap` creates it in code, after the highlight, so it draws on top |
| `fog_overlay.gd` (`FogOverlay`) | The translucent grey hex drawn over every tile that is seen but not discovered. `HexMap` creates it in code, between the roads and the outlines |
| `hex_highlight.gd` | Hover and selection outlines: a bright band with a dark ink border, readable on every terrain |
| `environment_generator.gd` (`EnvironmentGenerator`) | Random-frontier growth under `ALLOWED`: prefers neighbors, boosts regions under `MIN_REGION_SIZE`, damps regions over `MAX_REGION_SIZE`, then merges small regions. `extend()` grows an existing map into new cells without touching the old ones (they are frozen against merging), which is how the map enlarges. Tunables are at the top |
| `town_world.gd` (`TownWorld`) | 256×256 world of towns (small 1%, medium 0.5%, fortress 0.1%, never on neighboring spots). Each town links to its 1/2/4 nearest towns (small/medium/fortress) within 20 steps, in both directions. `to_dict`/`from_dict` are the map save's copy of the whole world -- towns as flat `[x, y, tier]` against a legend of tier **names**, links once per pair with the lower spot first, and `_buckets` rebuilt rather than stored. It is written down rather than regenerated because "a pure function of its seed" is a property of this code today and not a promise to the player |
| `road_network.gd` (`RoadNetwork`) | Routes roads along the town links with A*, using only shapes the sprites have (straight, 120° curve, 3/4/6-way). Roads stop at town edges and never cross a town tile. Terrain-independent, so a world always gives the same roads. `extend()` adds the links a window brings into reach, routing each inside its own box (around its two towns), so a road never moves once laid — growing the map only ever adds edges, sometimes turning a drawn road into a junction |
| `map_builder.gd` (`MapBuilder`) | Generates the map (`START_RECT`: 20×11 cells around cell (0, 0), which the camera centers on screen) and draws it as the player uncovers it. `rect` is what the map covers now: coming within `EXPAND_MARGIN` of an edge grows it by `EXPAND_BY` on that side (`expand_if_needed`, on arrival), generating the new land, its tiles and the roads it brings into reach, and redrawing the blends and roads of drawn tiles the new land touches. Everything already generated stays exactly as it is. Every cell is in one `State`: `HIDDEN` (the fog of war, nothing drawn), `UNDISCOVERED` (drawn under the grey fog, can't be walked to) or `DISCOVERED`. `create()` generates everything and draws `start_cells()`: the discovered center, where the player starts, ringed by six undiscovered tiles. `discover(cell)` takes the grey off a tile next to the player (`can_discover`), draws the tiles behind it as undiscovered, and sends the player walking onto it. `name_of(cell)` is what the tile is called: `_show` names it the first time the player lays eyes on it -- undiscovered land is land they can see, so seeing it is the encounter -- and the name is kept in `_names` and written into the save. It is stored rather than worked out again even though `TileNames.generate` is a pure function of the seed and the cell, for the reason the town world is written down: a place somebody has fought over must not be renamed by a later build widening a word list. `level_of(cell)` is the tile's level, in bands that widen as they go (band `n` is `n` tiles wide, so level `n` starts at the nth triangular number) -- what the side panel shows and the ceiling on what can drop there. `area_variant(cell)` says which battle backdrop the tile fights on -- its town tier if it has one, else `road` where a road runs, else `plain`. `can_farm(cell)` is any discovered tile with no walk under way -- farming asks nothing about where the player stands, because a run is a thing you choose to do rather than a step you take. `move_to(cell)` sends the player walking to a discovered tile over `route_to(cell)`, a shortest path of discovered tiles (`can_move_to` refuses anything else, and anything at all while `walking`); arriving emits `arrived(cell)` and discovers nothing by itself. `reveal_all()` discovers the lot. `origin` is the world spot at cell (0, 0): generated environments, plus that environment's town sprite where the world has a town. Before drawing, it clears any town within `START_TOWN_DISTANCE` (5) of the center and guarantees a small town exactly that far out, which a road links to cell (0, 0); that town's world spot is `start_town`. `_spot(cell)` is the crossing from map cells to world spots. `to_save()` and `restore()` are the map save's two ends: `restore` is the mirror of `create` and shorter than it, because the saved town world already has the clearing and the start town in it and the start road is among the saved roads, so it generates nothing and touches no town. It draws through `_draw_saved`, which lays every ground and road down first and refreshes each cell's blends once, rather than through `_show` -- `set_ground` refreshes a cell **and its six neighbours**, which is seven times the work when a whole map arrives at once |
| `tile_names.gd` (`TileNames`) | What a tile is called: a made-up proper word (a head syllable and a tail one, five hundred pairs) and a feature word taken from the environment, or from the settlement's tier where there is one -- "Bralmere Keep" says more about a fortress than "Bralmere Meadow" does. `generate` is a pure function of the map seed and the cell, under its own `"name"` tag, so what a place is called has nothing to do with which sprite it is drawn with or which backdrop it fights on. It names neither `MapBuilder` nor `TownWorld` -- the caller passes the environment and the tier's name -- so it is a table and a dice roll and nothing else |
| `map_save.gd` (`MapSave`) | The explored map at `user://map.json`: the seeds, the origin, the window, the whole town world, the land, the roads, the names of the tiles the player has seen, and what they have uncovered and where they stand. Version 2 added the names, written out as a plain `"x,y"` object rather than as rows against a legend -- a name is a whole word per cell and only the cells that have been looked at have one, so there is nothing for the alphabet to index; a version 1 save simply has none and its tiles are named again as they are asked about. `_tiles` and the fog are left out, being derived. The environments and the states are **one string per map row, one character per cell**, each indexing a legend written beside it -- which keeps the save small, keeps enum positions off the disk, and makes the env rows read as a picture of the map. `fingerprint(tileset)` is the SHA-256 of the three spritesheet tables a saved map is *read through* (`env_adjacency`, `blend_priority`, `legal_road_masks`) and nothing else, so a rebuilt sheet that only adds a variant costs nobody their map. `load_from` returns **two different nulls**: an empty `problem` is a first run, and a reason in it is a refusal. Never names `MapBuilder` -- that is the cycle Godot's checker bites on, so the states are raw ints here and `STATE_NAMES` is the legend |

`Scenes/main_scene.gd` has the exported `world_seed` and `map_seed` (0 = random; the used seeds are printed), `map_origin`, `zoom` (3 by default, whole numbers only so sprite pixels stay square) and `ui_scale` (2). It prints the clicked tile's environment weights and town connections, and builds the UI in code, so the scene file stays untouched while the editor has it open: a side panel flush against the right edge, running the full window height and hidden until a tile is selected — a green title bar with the title and an X at its right end, over a cream body holding one row per environment on the tile (a 16 px swatch cut from that environment's own hex-sheet tile, plus its percentage), a "Discover", a "Move here" and a "Farm" button pinned to the bottom — discovering the tile next to you walks you onto it, and "Move here" goes back to any tile already discovered (the camera follows until the player arrives), and "Farm" opens an endless run on a tile already taken, and an X top-right that closes the panel and calls `HexMap.deselect()`. Opposite it, an "Items" button in the top-left corner opens the bag: the same titled panel against the left edge, holding every item the world has handed over as tan squares straight on the cream body — the pack puts nothing between the two, so neither does this — each ringed in its rarity's colour above common. How full it is and what is in the purse share **one line at the top** -- the two things true of the whole bag rather than of anything in it, read in one glance, which also leaves the foot of the panel to the orb tray, which needs the width. The bag is **sectioned by level, highest first**, and inside a level sorted by rarity and then newest first; how full it is stands over the lot as `n / 40`, in `Palette.RUST` once it is, and the **orb tray is a footer at the very bottom**, after both of the two things that expand to fill the panel's height -- so it stands under whichever of them is up, the grid or an open stat block, and never scrolls out of sight, least of all while a piece is open, which is exactly when it is being used. It is a footer rather than a section because orbs are not sorted, filtered or chosen between, so it wants no heading and no buttons; `_refresh_orbs` is its own call beside `_refresh_gold`, because a kill moves one count and nothing else and there are ten or fifteen kills to a fight. **The tray has two states, and the bag decides which** -- the same resting-state-and-context pairing the character sheet beside it uses for its doll and its comparison. At rest it is what the player holds, every owned orb lit. With a piece open it answers a different question: the orbs that can do something to *that* piece stay lit and the rest go grey, and clicking a lit one spends it there and then. So there is no crafting row in the stat block and no arming step -- the thing already on screen becomes the thing you press. `_on_orb_pressed` applies first and spends second, so an orb that turns out to have nothing to do is never consumed, and because crafting adds nothing to the bag and takes nothing out of it the selection survives: `_refresh_bag` reopens the same index and the block simply says something new. `_orb_card` hovers **above** the square rather than beside it, which is the one direction there is room in -- one side of the tray is the screen edge and the other is the character sheet, which is also why it is added to the layer **after** the sheet: it overhangs that page for five of the eight orbs, and tree order is the whole of what decides which of the two the player sees -- and it carries `UITheme.theme()` itself, because a type variation means nothing to a Control with no themed ancestor. It is a **coin and a number**, not the word: `Coins.icon()` in front of the figure, which reads at the glance a footer is given rather than at the reading it is not. Each section's heading carries **Auto** and **Clear**: Clear throws away what is held at that level, Auto stops any more of it arriving. They are two buttons rather than one because a player who is finished with level 3 from now on has not necessarily finished with the three they are holding. A level with a rule on it and nothing in it keeps its heading, which is the only place the rule can be turned off again, and the rule is said in the heading in a word and a colour rather than left to the toggle's pressed face — the pack presses a button by drawing it a pixel lower, which is right for a press you are watching and far too quiet for a state you are reading off four headings at once. The character sheet is a **separate panel standing outside it**, against its right edge: the pack's own wood page next to its cream one, with the sides swapped so what you carry is on the left and what you wear is on the right, and no title bar of its own because the pack gives the spread one over the other page. It opens, closes and hides with the bag, and it has **two states**, decided by what the bag is showing rather than by anything it remembers itself. With nothing selected it is the doll: the pack's silhouette with the eight sockets laid **over the body they belong to** — helmet on the head, offhand on the shield arm, weapon on the sword arm, body on the chest, boots on the feet, and the jewellery in a row beneath, where a body says nothing about where a ring goes. The sockets are translucent (`ItemRarity.SOCKET_ALPHA`), which is the only thing that makes an overlay work: an opaque square would hide the very part it points at, and the pack washes its own sockets over its figure for the same reason. An empty ring or amulet socket carries the pack's faint mark for it. `DOLL_SOCKETS` is measured off the sprite and placed by hand — no container expresses "over the shield hand" — and `test_inventory` checks no two sockets overlap and none runs off the page. `DOLL_SCALE` is set by that layout rather than by taste: head, chest and feet are 17 and 15 sprite pixels apart, so a 40 px square needs at least 2.7 to clear its neighbours, and whole numbers only, for the reason `zoom` is. With a bag item selected the **comparison takes the doll's place**: the piece that item would replace, standing beside that item's own block, at `WORN_WIDTH` (the bag's own width, so the two columns wrap alike). The socket is `Equipment.sockets_for(item)[0]`, exactly the one the Equip button targets, so the page shows precisely what pressing Equip would take off, and rings and the shield-or-torch offhand are settled without a second rule. The panel's own face changes with the state — the pack's wood page under the doll, its cream one under a stat block, because the darker half of the rarity ramp was picked to be read on white and vanishes into wood — and `_layout_ui` measures and re-centres it each time, twice, for the reason the tile panel is measured twice. Unequip from the comparison keeps the bag's selection open, finding the piece again by identity because what comes back into the bag moves every index after it; Unequip on an opened socket goes back to the doll as it always did. Clicking a square, or a filled socket, puts that item's stat block in the grid's place — name and rarity in that rarity's colour, then what the piece is worth and what it rolled — with Equip and **Discard** over a Back button, or Unequip over one. The block says what the piece **is** and nothing about what it would replace: the comparison is the worn piece standing whole beside it, and a second one written out as signed numbers under the stats said the same thing twice in two different languages, so a selected piece and an equipped one now read exactly alike wherever either is shown. The lines scroll and the buttons under them do not, so a long piece can never push Equip off the bottom of the window. A worn piece has no Discard of its own — the cap is on the bag alone, so nothing presses the player to destroy what they are wearing — and a full bag greys Unequip rather than destroying something to make room for a piece being looked at. Only ever one of the two is open: they share the space. The squares on the panel at the end of a fight open the same way, in the verdict's place. The grid scrolls by wheel and by dragging it, and never shows a scrollbar; a press that travels is a drag and one that does not is a click, the same rule `HexMap` uses to tell a pan from a tile click. The button and the panel both go while a fight is on — a `Control` left in that corner would take the mouse before the fight saw it and quietly eat the player's swings. `inventory_path` and `map_path` are exported beside the seeds so tests can point them away from the real saves. The map is written at the end of `_ready` (the world is decided the moment it is generated), on every arrival (the one place the map's own state changes) and in `_exit_tree`; a refused save blocks all three. A save that cannot be honoured builds no map at all and puts up a panel saying so, naming the file.

## Combat code (`Scenes/Combat/`, `Scenes/Enemies/`)
A tile has to be taken before it can be discovered: a lineup of enemies against a clock, both of them the tile's own. What the world put there says which fight it is (`Encounter.PROFILES`, keyed by `MapBuilder.area_variant`): open land and roads field ten in thirty seconds ending on an elite, and a **settlement of any tier is a set piece** -- fifteen in a minute, an elite every fifth and a **boss** last, which is the only place a boss is ever rolled. A farm run on a settlement keeps that elite rhythm and never its boss. How hard they hit back grows with the walk -- see `level_of` and `HP_GROWTH` above. A click takes off what the player's gear is worth, crits at its crit chance for its crit damage on top, and the weapon swings itself `attack_speed` times a second beside that. Winning calls `MapBuilder.discover` exactly as pressing Discover used to; losing changes nothing and can be retried at once.

A tile already taken can be **farmed** instead (`MapBuilder.can_farm`, the Farm button beside Discover and Move here): the same arena and the same terrain's enemies, coming forever, with no clock and nothing riding on it. Nothing is won but what the bodies were carrying, and the only way out is the Terminate button, up in the top-right corner where a frantic click cannot reach it. Every body also rolls for an **orb**, on its own generator and its own curve, **beside** the gear rather than against it -- so one body can hand over both, and the two rates are independent numbers rather than one number split in two. An orb is thrown out of the body exactly as a find is (`_show_find`, which both go through), and plain: it has no rarity, and a glow borrowed off that ramp would say it had one. It never enters `_drops`, so the loot counter, `DropsView`, the discard flow, `bag_room` and the autodiscard filter have nothing to say about it, and `_orb_label` says `+n orbs` under the verdict beside the gold. Every body also hands over a **purse**, which is not rolled for: gold falls off every body where gear falls off about one, and the fight says once under the verdict what it earned. Both fights carry a **loot counter** in the bottom-right corner wearing the newest find and the count, which opens the run's whole haul, and everything a body drops -- its purse, its gear and its orbs -- **falls out of it into the arena** and lies there before it fades, which is the one thing said while the fight is still on; a run has no verdict to wait for, so the counter and its list are where a find is then read properly. Opening a find in either list gives a Discard button, which is how a run that has turned up more than the bag will hold is sorted out before it banks. How much room is left is said by the **counter's own face**, which ramps from the pack's green to its red as the bag fills, and the sentence explaining it stands inside the counter's panel rather than out in the arena -- a colour is read out of the corner of an eye without taking any room, and the words belong where the player has already asked what the run is carrying, which is also the one place they can do something about it. A level the player has ruled out never appears at all -- not in the counter, never thrown into the arena, not in either list -- and the number thrown away is said once, under the verdict.

| File | Contents |
|---|---|
| `enemy_roster.gd` (`EnemyRoster`) | Every enemy under `Assets/Enemies`: its `Tier` (COMMON/ELITE/BOSS), its `Size`, its `Facing` (the packs disagree; `CombatActor` mirrors only the ones drawn facing right, so nobody walks in backwards), the environments it lives on, and its sheet per animation. Health is not written per enemy — `SIZE_HP` and `TIER_HP` multiply into `hp_modifier`, so the whole curve is tuned from two tables. `weight` is written per entry, because being numerous has little to do with being big: whole numbers on one absolute scale, commons 30-100, elites 8-20, bosses 1-4, bands that never overlap. `pick` draws weighted by it, and a slime at 100 is the commonest thing on every terrain. `frame` and `bounds` are measured, not guessed (see the gotcha below) |
| `encounter.gd` (`Encounter`) | The rules, with no nodes: `for_tile(cell, env, variant)` rolls the tile's lineup, seeded from the cell so a tile always fields the same fight, and keeps `env` -- the terrain picked the enemies and it picks the backdrop. `PROFILES` is what the `variant` buys: one table saying, per thing the world can put on a tile, how many enemies, how long a clock, how often an elite and whether the last one is a **boss**. Open land and roads are `ORDINARY` (the old ten in thirty, ending on an elite), and village, town and fortress share one `SETTLEMENT` entry -- fifteen in sixty, an elite every fifth, a boss last -- because what makes a town a longer fight is that people live there, not how many of them. A fight built and told nothing is the ordinary one, which is what every `Encounter` made by hand gets. `farm(cell, env, variant)` is the same fight `endless`: one enemy to start, and `_append_enemy` puts the next on the end of the lineup the moment the last one falls, so it is never finished; it takes the tile's `elite_every` and never its boss -- a boss is what a set piece ends on, and a run does not end. `_append_enemy` is the one place that knows how an enemy joins a fight, which is what keeps a tile's lineup and a run's thousandth enemy built alike -- both from `tier_for(position)`, the fight's own rule, which is also why `on_elite()` asks `EnemyRoster.tier_of` rather than counting to the end. `stop()` ends a run at the player's word (a win, because a run is not a thing that can be lost) and `kills()` is the score it shows instead of a countdown. A settlement's last enemy is the only boss the game rolls. `always_drop` makes every body carry something -- nothing in the game turns it on, it is what lets the tests and the screenshot scripts show a pouch with three finds in it without grinding out the hundred-odd kills a 3% chance takes. `arm(stats)` reads `Equipment.totals()` once as the fight opens — the bag is shut while a fight is on, so there is nothing to keep live — and keeps `drop_rate` beside the four combat numbers, which is handed to `LootTable.roll` on every death, and a fight nobody arms does `BARE_DAMAGE` a click with nothing swinging, which is the game this was before gear meant anything. `hit()` is one blow, `advance(delta)` runs the clock and the weapon's own swings, `won`/`lost` end it. Every death also emits `gold_dropped` and adds to `gold`, the fight's running purse -- `gold_of` is `base_gold(cell)` times the body's own `hp_modifier`, so a purse is worth exactly what the body was worth to kill and nobody keeps a second table in step with the first. `base_gold` grows with the walk **both ways at once**, `(BASE_GOLD + GOLD_PER_STEP * steps) * GOLD_GROWTH ^ steps`, off the same smooth distance the health does rather than the banded `level_of` -- so an ordinary common body in the middle of the map is worth exactly one gold, which is where the whole curve is pinned. `GOLD_GROWTH` is set near `LootTable.LEVEL_GROWTH` rather than near `HP_GROWTH`, so a purse keeps pace with the gear that has to kill for it rather than with the health it has to get through. `hit_landed(amount, crit, automatic)` is what the view draws numbers from. Crit damage is what a crit *adds*: 50 is half again, and `arm` clamps crit chance to `CRIT_CAP` so a pile of gear -- or a piece from a save written before chances stopped being multiplied -- can never make every hit a crit. An automatic swing only earns while an enemy is standing there, so nothing banks through a walk-in. Health is `hp_modifier` over a base that grows **exponentially** with the distance from cell (0, 0) -- `BASE_HP * HP_GROWTH ^ steps` -- so the frontier pulls away from whatever the player is carrying and farming is how they catch up. `BASE_HP` is tuned so the first ring is what it always was, and `HP_GROWTH` is the dial for how fast the map gets hard |
| `drops_view.gd` (`DropsView`) | What a fight has turned up, as a grid of `ItemSlot` squares one of which can be opened into an `ItemDetails` block. The verdict panel and the loot popup are both one of these rather than the same layout written twice; the grid and the details swap rather than stack, the way `_bag_scroll` and `_bag_detail` do on the item panel. `resized_contents` is how an owner that centres it knows to measure again. With `discardable` set, an open drop carries a Discard button over its Back — the view never touches its own list, it emits `discarded(item)` and the owner takes it out and fills again, so there is one place that knows what the run is carrying |
| `combat_actor.gd` (`CombatActor`) | An `AnimatedSprite2D` built from a sheet at runtime, as `PlayerToken` is. Serves both sides. Scaled and stood up by its *idle* frames, so `position` is the middle of its feet whatever the attack or death frames sprawl into |
| `combat_scene.tscn` / `combat_scene.gd` (`CombatScene`) | The view: backdrop, the two fighters, the HUD, the clicks, the verdict. **Centred on the bottom edge**, the nameplate: the enemy's name and a `HealthBar`, standing on the arena with **no panel behind them** exactly as the place's name and the clock do on the top edge and for the same reason — so the name is a `_hud_label` in bone with its dark outline, and the bar brings its own border. The bar wears that enemy's tier as its frame — `Encounter.tier_in`, the same call the pips read, so the two can never disagree about what is standing there. It is parked on an edge rather than floating over the enemy's head because health is a thing the player watches continuously and a panel that walks in with the enemy and slides about under it is the worst place to read a number off; it also stops the damage numbers and the nameplate competing for the air over the body. The bottom middle specifically, so that it sits directly under the pip bar and the clock and the whole of how the fight is going reads down one column. The clock and the bar stand **centred on the top edge with no panel behind them** — they are what the player watches, and a panel only puts furniture round them — so each carries its own dark border instead (`BAR_BORDER`, and `LABEL_OUTLINE` on every word up there, through `_hud_label`), which is what has to read against a backdrop rather than against wood; `_place_corners` centres the column every frame, for the same `ui_scale` reason it places everything else. The clock bar is cut to `KillPips.WIDTH` less its border so the two are one column to the pixel. The pip bar is **above** the clock — the bar is the fight and the clock is what the fight is measured against, so the measure sits under the thing it measures — and inside the clock the number sits under its own bar, keeping the two bars adjacent. `_clock_color` ramps the bar **and the number together** from green through `Palette.GOLD` to the damage red as the clock runs out (`CLOCK_GREEN`, `CLOCK_AMBER`, as shares of the whole so retuning `Encounter.SECONDS` retunes them): a ramp rather than a switch at some number of seconds, because the colour is read out of the corner of an eye and an ambering bar says hurry a good deal earlier than one that turns red all at once. The corner counter (`_loot_button`) wears the newest drop's own icon rather than a bag nobody drew, and opens `_loot_panel`; it stands in the **bottom-right** corner, out of the way of the nameplate that has the middle of that edge. Its **face** is how full the bag is: `_tint_loot_button` ramps a tint over the pack's green button art from `FACE_GREEN` through `Palette.GOLD` to `FACE_DANGER` (the pack's own red, the key its danger button is played in) as `bag_room` runs out, a ramp rather than a step for the same reason `_clock_color` ramps. The tint goes on **copies of the theme's own styleboxes**, one per `UITheme.STATES`, rather than on the node — `modulate` on the Button would take the find's icon and the count with it, and what has to change colour is the frame behind them. A hit floats its number off the enemy at twice Pixellari's native size, and a crit at three times in the damage red with an exclamation mark, so which kind of blow landed is read without reading the number. `_show_find` throws each find and each orb out of the body instead of announcing it in the corner, and `_finds_shown` counts them, which is all anything downstream ever asks. `_place_corners` puts the counter and Terminate where they go every frame rather than anchoring them, because both are scaled by `ui_scale` and an anchor knows nothing about that. Endlessly the clock is hidden and the tally counts up. A `CanvasLayer` the main scene adds in front of the map rather than a scene change — the map holds a whole generated world in memory that a scene change would throw away, so it is hidden and its `process_mode` disabled instead. Drawn height comes from `SIZE_HEIGHT`, so a slime is knee-high and a boss looms. The backdrop is `Assets/Area/<env>_<variant>_<n>.png`, the environment from the encounter, the variant from `MapBuilder.area_variant`, and `n` from `layout_for(cell)` — every place is drawn `AREA_LAYOUTS` (4) ways, and the pick is seeded from the cell under its own `"backdrop"` tag, so a tile always fights on the same one however often it is attempted but which picture it is has nothing to do with who walks in. `backdrop_for` clamps a layout past the end and falls back to `grass_plain_1` rather than leaving a fight with no picture behind it. It is also where the player's autodiscard rule is applied: `_on_loot_dropped` is the only listener to `Encounter.loot_dropped` and forks into `loot_kept` and `loot_discarded`, which is what the rest of the game hears. A find at a ruled-out level is counted in `_auto_discarded` and nothing else — no square, no counter, nothing thrown — and the count is said once under the verdict. `gold_gained` is a body's purse passed on, for the reason `loot_kept` is. `_throw` is the one arc everything a body drops travels on -- across at a steady rate while the height goes up and comes back down, then lying where it fell before it fades and frees itself -- from `_drop_origin`, the enemy itself (a drop lands the frame it dies, so the body is still standing there). `_show_coins` throws a purse as `Coins.count_for` coins, so a richer body visibly pays more without the arena filling up; `_show_find` throws one find or orb, and above common stands a `LootBeam` over it in the rarity's **ring** colour (`BEAM_SCALE`, `BEAM_ALPHA`, `BEAM_LIFT`, which sets its foot on the piece rather than leaving it floating over one) -- the ring half of the ramp rather than the text half, because a find is thrown against a snowfield or a noon desert and that is what that half was picked for. It is the second hand-rolled tween in the file beside `_show_damage`, there being no effect helper, and it is what says something was found or earned while the fight is still on. `_gold_label` still says the total once under the verdict, behind a coin rather than the word and in the panel's own colour rather than `Palette.GOLD` -- that hex is the unique item step, and spending it here would put one colour on a currency and on an item's name in the same panel. `bag_room` is how much room the bag has left (`-1` when nobody has said), which is what the counter's face is tinted from and what puts `_warning` up inside `_loot_panel` — a line over the list rather than a panel of its own, flipped through `_show_warning` because it changes the popup's height and the popup is centred on what it holds; `drop_discarded` is a find the player threw away by hand from either list |

## Items (`Scenes/Items/`)
Every enemy killed rolls for gear and hands over a purse, and both are the player's whatever the fight does next — a lost fight still leaves the kills that were made. Gold is the half that always lands: gear falls off about one body in thirty and gold off all of them, and nothing spends it yet. A drop is its own thing: it rolls a rarity off the enemy that carried it and modifiers off that rarity's band, so two Wooden Swords are two different swords and nothing stacks. **The offensive stats are live, and so is drop rate.** What the player wears decides what a click takes off, how often it crits and how hard, how fast the weapon swings on its own, and how often a body leaves anything at all — the Gold Ring is the piece that finds things, and the jewellery is where offence lands that is not the weapon's: flat damage and crit among its affixes, and **global** percents that scale what the whole set is worth rather than what the ring is. Everything else — armour, health, leech, the attributes — is still rolled, saved and shown and waits on the systems that would give it something to do (nothing can hurt the player yet, so there is nothing for a defence to defend against), and the resistances are off every piece until there is.

## Sprites
The sprites are generated by `AI-sprites-generator/` (Python, exported through Aseprite). Its README holds the palette, geometry, adjacency table and blend rules. `AI-sprites/` is build output: change the generator, preview with `qa.py` and get the user's approval, then run `build.py`.
The **battle backdrops** are the other generated set and do not go through Aseprite: `build_areas.py` writes 120 PNGs straight into `Assets/Area/`. Each of the six environments builds in its own way out of its own pieces -- `bld_<env>.py` for what it builds with, `lay_<env>.py` for its twelve plans, and `areabuild.py` for only what every place shares. The README's *Battle backdrops* section holds the six cultures and the rules a fortress is composed to. `qa.py areas <tag> [env...]` previews and checks (scope it to one environment while iterating -- a full pass is over two minutes, past the point where it gets backgrounded), `qa.py audit` resolves every piece name in under a second, and `qa.py frozen check` holds the desert to twenty hashes because it is finished and must not move. **Close the Godot editor before `build_areas.py`**: it locks the PNGs it has imported, and the build now refuses to start rather than leaving `Assets/Area/` half old and half new.
The six per-environment slimes are generated too: `slimes.py` swaps the blue slime pack's body ramp for each environment's `hexlib.PALETTE` ramp, `qa.py slimes <tag>` previews and checks them, and `build_slimes.py` writes them to `Assets/Enemies/<Env> Slime/`. They skip Aseprite and the atlas -- the source is already a PNG pack and they ship as ordinary RGBA sprites under `Assets/`.
**The interface is not generated, with one exception.** The exception is the combat nameplate's health bar: `hpbar.py` draws its nine parts (a left cap, a right cap and a track, in three tier colourways) in `hexlib.PALETTE`, `qa.py hpbar <tag>` previews and checks them, and `build_hpbar.py` writes them loose into `Assets/UI/` and reads every file back. They skip Aseprite and the atlas the way the slimes do, and they stay out of `ui_sheet.png` and `ui_sheet.json` the way the pip parts do — a part is drawn at its own size and never stretched, so it has no nine-slice, and `test_ui_theme` counts that sheet exactly. It is drawn rather than cut because no pack holds it: `Pixel UI pack 3/06.png` is the flat capsule the pips come off and its three tier bands differ only in colour, and `04.png` is on disk as `Assets/bars.png` already, turned down by `CombatScene._bar` for being a glossier style than the rest of the interface. Everything else is cut from the bought Craftpix pack under `Assets/Potential/2D Pixel UI/` by `tools/ui_kit.py`, which writes `Assets/UI/` (the sheet, the loose sprites and `ui_sheet.json`) and a tiling preview at `tools/qa/ui_kit_tiling.png`. The pack ships finished panels and buttons rather than a slice kit, so that file is where it is written down which rectangle of which pack sheet is which sprite and where its nine-slice margins fall. Both panels are the pack's own art, cut whole; the one thing that is not is the button, because the pack has one colour and three states — the danger and disabled faces are palette swaps of the green, mapped by hue and saturation with each step's lightness kept, the way `slimes.py` recolours the blue slime.
The same script also cuts the combat HUD's **kill-pip bar** from a second bought pack, `Assets/Potential/Pixel UI pack 3/06.png`, whose capsule the 2D Pixel UI pack has no equivalent of. The game needs that capsule ten and fifteen pips long and the pack ships it at five, so what is cut is not the bar but the three parts it is built from — a head, a body and a tail, each in the three tier colourways and in the pack's empty grey, twelve loose PNGs into `Assets/UI/` and never into the sheet, with a preview at `tools/qa/ui_kit_pips.png` showing the assembled bar at all eleven drain states. That is possible because the capsule sits on a rigid **4 px segment pitch** — measured off the pixels and checked against both the 1/5 and the 5/5 step, an n-segment fill is always columns `1 .. 4n+1`, with col 0 the black left edge, cols 1–4 the segment carrying the rounded left shoulder, cols 5–8 onward the repeating interior segment, and cols 25–26 the rounded right end. The right end is taken off the **empty** capsule for every colourway, because that is how the pack draws the end of its own full bar. The fill steps are left uncut (a pip is a whole enemy, not a fraction of one) and so is the silver colourway — there is no fourth tier.

The same file also cuts the eight **orb icons** (`ORBS`, `orbs()`) off `Assets/Potential/OreAndGem/OreGemSpritesheet.png`, a 10x5 grid of 50 gems on an exact 32 px pitch, so an entry is only ever a cell of it. They go to `Assets/Orbs/` rather than `Assets/Gear/` -- an orb is not gear and `OrbTable` loads it by its own `ROOT`. The picks are made for distinctness across the tray as much as for the colours Path of Exile trained the idea into: the eight stand side by side in one row, so no two may read as the same stone at a glance. The one thing `gear()` does not have to care about is that `orbs()` centres the trimmed art on an **even** offset -- `OrbSlot` draws at half size, and a 2:1 step keeps whichever column is even, so an odd offset shifts the art into the other phase and loses a column it did not have to. `tools/qa/ui_kit_orbs.png` shows every orb twice, at source size and at the 16 px the tray draws it, because the halving is the only thing about these icons that can go wrong.
The **loot beam** is cut the same way and for the same reason, by `tools/loot_beam.py`: the "Mini Falem" effect out of the bought pack under `Assets/Potential/Effects`, which ships as loose 16 px frames in nine colourways, written out as one fifteen-frame strip at `Assets/Effects/loot_beam.png`. Only the white colourway is taken -- see `LootBeam` for why one sheet covers every rarity -- and it never enters `ui_sheet.png`, being an effect rather than a theme sprite.

The same file also cuts the **gear icons** (`GEAR`, `gear()`), because it is where it is written down which rectangle of which bought sheet is which sprite and a second script saying that a second way is how the two drift apart. They are not theme sprites: they go to `Assets/Gear/` as loose 32×32 PNGs for `LootTable.ROOT` to load by path, never into `ui_sheet.png` or `ui_sheet.json`, and they skip `check()` for the reason the close button does — an icon is drawn, never stretched, so it has no nine-slice to hold flat. `PARTS` cuts the equipment page's own furniture the same way — the pack's silhouette and its two empty-socket marks — loose into `Assets/UI/`. The preview is `tools/qa/ui_kit_gear.png`, every gear icon the game has on the bag's tan socket, because the one thing that can go wrong is whether the new ones look pasted in beside the old. Ring and amulet come off `Icons.png` (a 6-column grid on a 16 px pitch, rows *not* evenly spaced — each entry's y and height are that one icon's measured extent), doubled to land near the size of the RPG pack's 28 px art, which doubles their pixel too; that is why only the two pieces no pack draws are taken from it, and the torch is the RPG pack's own.

`Main_tiles.png` is laid out as a family: four colourways (a brown or green header over a cream or a brown body) by three frame weights, plus header-less bodies, a big cream panel, scrollbar rails and thumbs, close buttons and slot tiles. The game takes the header-less brown body, the big cream panel, and the green title bar **cut off its panel rather than taken with it** — the pack draws bar and body as one sprite, which fixes the bar at 13 px, and Pixellari needs 16 to stay legible. Cut on its own the bar is a nine-slice like any other and grows to whatever the title needs, with the body panel stacked under it. That is what `main_scene._titled_panel` builds, and `_body_of` hands back the VBox to fill.

The close button is the pack's own drawn X, not the letter typed on a green button: one 9×10 icon the pack uses on every panel size, tinted to the surface it sits on, so the green one is cut for the green bar. The pack draws it once, so the other three states come from the pack's own rules — pressed is the face a pixel lower with its drop shadow gone, which is how the pack presses every button it has, and hover lifts the frame's lightness by the step measured off the pack's green face (#50a978 → #68c97e, the same lift that takes its shade #478773 to #50a978).

The earlier AI-generated UI sheet (`ui.py`, `build_ui.py`, `qa.py ui <tag>` and `AI-sprites/ui/`) is no longer wired to anything.
Both builds share `buildlib.py`: the Aseprite call, the pass that reads every exported PNG back and compares it to the source pixels, and the report. Which environments each road material is used on lives in `roads.py` (`MATERIAL_ENVS`), and is what ships to the engine as JSON meta `road_materials`.

## Rules and gotchas
- **Rules come from the JSON meta:** `blend_rule`, `blend_priority` and `env_adjacency`, all read through `SheetMeta` — `HexTileset.can_border` and `EnvironmentGenerator.allowed()` are the same table, so the generator cannot produce a border the sprites can't draw.
- **Map origins must be on even rows**, otherwise world neighbors don't match on-screen neighbors (`MapBuilder` asserts this).
- **Test pattern:** everything in `tests/` extends `tests/harness.gd`, which starts `_run` deferred and holds `_check`, the failure count, `_report("suite name")` and the shared `WORLD_SEED`. Each `_test_*` function returns `true` and `_run` checks that it did, so a script error counts as a failure.
- **Editor conflicts:** the Godot editor is often open. After changing `project.godot` or `.tscn` files outside it, reload the project so the editor doesn't overwrite them.
- **A nine-slice margin is only correct if what it leaves over is flat:** a `StyleBoxTexture` repeats the centre and the four edge cells, so every row the top and bottom bands tile horizontally, and every column the side bands tile vertically, has to be one colour or the seams show. `tools/ui_kit.py check()` re-reads each sprite and refuses to export one that is not — which is how the button margins were found (bottom 3 looked right and put one pixel of the corner bevel into a tiled column).
- **Pixellari renders cleanly only at 16 px**, its native size; below about 14 the glyphs break up. To make the interface smaller, lower `ui_scale` rather than the theme's `FONT_SIZE`.
- **A floating panel cannot be a Godot tooltip, and that is why `OrbCard` is not one.** A tooltip is its own popup window, so it cannot inherit the bag panel's `ui_scale` transform; the only way to make it match the panel beside it would be to ask for type at `FONT_SIZE * ui_scale`, and by the rule above that comes back interpolated next to art that is not. So a card like this is an ordinary Control on the scene's own `CanvasLayer`, scaled by `ui_scale` and placed by hand -- which is what `CombatScene`'s full-bag warning already is, for the same reason.
- **Enemy sheet geometry is measured, not guessed:** frame widths run 32 to 245 px with no relation to the sheet height, and a greatest-common-divisor guess gets Dwarf Warrior and Mimic wrong. The frame width is the smallest divisor of every sheet width in the pack where each frame boundary lands on a fully transparent column; `test_enemies.gd` re-checks that against the sprites, so adding an enemy means measuring it the same way.
- **A backdrop keeps the skeleton:** the horizon is on row 200 and the land starts on row 202 in all thirty, so an enemy drawn at a given height stands in the same place whatever the backdrop; `qa.py areas` fails if a scene moves it. The pale top of the sky is the cloud ceiling drawn over the ramp, not a band in it, and the road variant lays its track *across* the shot -- at 576 px wide a vanishing point is four pixels and reads as a spike.
- **Recolours never redraw:** an environment slime is a pixel-for-pixel palette swap of the baseline, so its silhouette and animation are the baseline's and `EnemyRoster` can share one `frame` and one `bounds` across all six. `qa.py slimes` fails on a single changed alpha pixel.
- **Orbs follow gold, with one difference: gold is one number and orbs are eight.** A discovery fight banks each orb as it lands and a run pouches its own in `_fight_orbs` until it ends, exactly as the gold beside it -- and `_bank_farm_loot` banks them **above** its empty-pouch early return for the same reason the gold is banked there, because a run that turned up currency and no gear has still earned its way. Nothing can refuse an orb either: the bag's cap has nothing to say about a count, no autodiscard rule filters it, and there is no Discard for it.
- **Gold follows loot, with one difference: nothing can refuse it.** A discovery fight banks each purse as it lands and a run pouches its own in `_fight_gold` until it ends, exactly as their finds are handled and for exactly the same reasons. But a purse is a number rather than a square, so the bag's cap has nothing to say about it, an autodiscard rule never filters it, and there is no Discard for it -- a run that threw every find away still earned its way. It is also the half that is never written as a word: the coin stands for it in both places it is said, and `_show_coins` throws it out of the body so the one thing that always drops is the one thing that was never drawn. Which is also why `_bank_farm_loot` banks the gold **before** its empty-pouch early return.
- **Farm loot belongs to the run, not the kill:** a discovery fight writes each drop to disk as it lands (`main_scene._on_loot_dropped`), because it is over in half a minute and closing the game mid-fight must not cost a find. A run could go an hour and has no end of its own, so its finds wait in `_fight_drops` and go into the bag in one write when it ends. Both ways out bank -- `_on_combat_finished` and `_exit_tree` -- and `_banked` is what keeps the second from repeating the first.
- **An endless run has no clock and no loss:** `Encounter.advance` does not touch `time_left` while `endless`, so the only two ways a run finishes are `stop()` and `give_up()`. Anything reading `time_left`, `remaining()` or `enemies` to decide something has to ask `endless` first -- the lineup grows, so `lineup.size()` is the only honest end of it. The one thing a run does keep off its tile is `elite_every`, which is the whole of its rhythm.
- **Loot belongs to the attempt, not the tile:** a tile's enemies are seeded from its cell, so the same tile always fields the same fight, but `Encounter.loot_rng` is left unseeded (a `RandomNumberGenerator` seeds itself, so there is no `randomize()` to add) and re-fighting a tile can turn up something else. Tests set the seed themselves.
- **A generated item's level and base stats never change again; its rarity and modifiers are what an orb is for.** An item's level and its scaled base stats are worked out once, when it is rolled, and stored on it and in the save. Crafting is the first verb that changes a held piece at all -- `item.gd`'s own docstring anticipated it -- and it changes only the two things `OrbTable` is allowed to touch, and only from the bag, where no fight is holding a second reference to the same object. Before this, base stats were looked up from `LootTable` on every call so that retuning a sword retuned every sword already held; that is what made a held piece drift, and it is gone. `LootTable` is still where a *new* piece is rolled from and still owns `slot_of`, `icon`, `affixes` and the labels. Stats are stored as the number they display -- whole, or one decimal for a rate -- so the save round-trips exactly and the stat block can never disagree with the fight. An `Item` built by hand (tests do this) has to be given `stats`, or it is worth nothing.
- **A level is a multiplier *and* a per-stat flat step.** `LootTable.scale` is the only place that knows what a level does to a number. `LEVEL_FLAT` carries one entry per stat because an absolute step has to suit the size of the number it is added to: a point a level is everything to damage, which starts at 1, and a rounding error to crit damage, which starts at 50. A multiplier alone would leave a sword reading "Damage 1" for four levels. A `PERCENT` or `GLOBAL` modifier takes the multiplier only -- it is already a percentage of a stat that grew -- and a `PLAYER` modifier takes neither, because `+4s on the fight clock` scaled would delete the only way to lose a fight. A **flat modifier may name its own step** (`level_flat`) where the stat's was sized for a different piece: base damage keeps its whole point a level, which is what makes a sword gain a visible point each time, while `added_damage` takes a quarter, because four sockets roll it and only one of them is the weapon.
- **A tile's level is a ceiling, not a payout.** A drop rolls its level evenly up to `level_of(cell) + LootTable.TIER_LEVEL[tier]`, with rarity lifting the floor (`ItemRarity.LEVEL_FLOOR`), so fighting deeper improves the odds rather than the prize and farming is how the top of a tile's range is eventually rolled. A single drop is therefore a poor measure of a tile: the balance numbers describe a piece rolled at the ceiling.
- **Monsters outgrow gear on purpose.** Health climbs `HP_GROWTH` per *hex step* while gear climbs `LEVEL_GROWTH` per *level*, and levels arrive in bands that widen -- so the gear exponent grows with the square root of the distance and the health exponent with the distance itself. The player is ahead through the early map and falls behind past the middle distance. Since the clock came down to 30 seconds the frontier is past what a **plain** set of commons can beat, and that is the design rather than a regression: reaching it means farming for better rolls. Farming cannot raise the level a tile drops at — that ceiling is the tile's own — so what a long run buys is modifiers. `test_combat._test_a_won_fight` pins all three ends of that: the first ring stays beatable bare-handed, a plain set at the far edge must need **8 clicks a second or more** (it is out of reach), and a farmed set of rares must bring it under 8 and stay over 1 (not a walkover). `HP_GROWTH`, `LEVEL_GROWTH` and `LEVEL_FLAT` are the dials, and `Encounter.SECONDS` is now one too — over a third of a 30-second fight is `WALK_IN` and `DEATH` animation, so shortening those is the other way to give a fight back its time.
- **Only the offensive stats and drop rate are wired up:** `damage`, `crit_chance`, `crit_damage` and `attack_speed` are read by `Encounter` and decide what a blow is worth; `drop_rate` is read by the same `arm()` and handed to `LootTable.roll`, where it lifts the chance a body leaves anything, capped where that chance has always been capped. Every other stat is rolled, saved and shown and does nothing. Nothing can hurt the player — the clock is still the only way to lose — so armour, health, block, dodge and the resistances have nothing to defend against, and giving them a job means giving the player a health pool first.
- **The bag is read one way and emptied another, and they are not one reversed.** `Inventory.order()` is level-major, because that is how a player looks for a piece; `worst_first()` is rarity-major, because that is what "worst" means when something has to go — a level-2 elite is worth keeping over a level-9 common. `test_inventory._test_bag_order` pins both, and that they differ.
- **An autodiscarded find is filtered in exactly one place, `CombatScene._on_loot_dropped`, and the fight is what everything downstream believes.** The main scene no longer listens to `Encounter.loot_dropped` at all; a second listener applying the rule a second way is how the counter, the pouch and the bag would come to disagree about what a run found.
- **A comparison is against one socket, and it is the socket Equip targets.** `_show_item` and the character sheet both ask `Equipment.sockets_for(item)[0]`, so what Equip would take off is exactly the piece shown beside the one being judged. A ring compares against the emptiest finger, which is the one it would actually go on. The comparison is that piece and only that piece — the stat block is the same block for a bag item and a worn one. `ItemDetails.fill` still takes an `against` and `ItemDetails.deltas` still works it out, tested on its own; nothing in the bag passes one.
- **The character sheet only changes while something is selected.** The doll is the page's resting state and is untouched — same silhouette, same hand-placed sockets, same wood panel, same centring. The comparison is what is shown *instead of* it for as long as a bag square is open, and closing the square brings the doll straight back.
- **A piece is in the bag or in a socket, never both:** `Inventory.equip`/`unequip` move it, which is why they live on `Inventory` rather than on `Equipment` — the bag and the worn set have to change together, and every caller getting that right separately is the same bug waiting in as many places as there are callers.
- **What an item shows, what it can roll and what it can scale are three different lists:** `stats` is the piece's own, `affixes` is a permission to roll a flat modifier for a stat it has none of, and `globals` is a permission to scale the whole set's. Neither permission reaches a stat block, so adding a stat to one widens the modifier pool without lengthening what the player reads. Neither may overlap `stats`, and an affix with no `FLAT` modifier naming it -- or a global with no `GLOBAL` one -- is unreachable; `test_inventory._test_items` fails on all of it.
- **A `GLOBAL` modifier belongs to the player, so it is applied by `Equipment.totals` and never by `Item.effective_stats`.** A ring has no damage of its own for "+14% increased Damage" to scale; the sword's is exactly what it means, and the one place both are in hand is the set. Two of them add rather than compound, which is the arithmetic a player does in their head. It writes the same line a `PERCENT` one does, and honestly so: with one weapon between them, a sword's increased damage and a ring's are the same claim about the same number.
- **Every modifier value is a whole number:** it means one `randi_range` a modifier, it means the save holds `14` rather than `14.0`, and it means a round-tripped item can be compared with `==` instead of an epsilon. Base stats may hold a float (`attack_speed`) precisely because they live in a const table and never cross the file.
- **A square in the bag takes no mouse input at all** (`MOUSE_FILTER_IGNORE`): the grid sits in a `ScrollContainer` that has to see every press to tell a drag from a click, and a square that swallowed the press would break every drag that started on one — which is most of them. Which square was clicked is worked out from where the cursor is.
- **A `Control`'s `size` is clamped to its minimum as it is set, and a `TextureRect`'s minimum is its texture until `expand_mode` says otherwise.** So asking a 32 px icon for a 16 px size while the mode is still the default gets 32, and lowering the minimum afterwards does not shrink what was already set -- `OrbSlot` sets `expand_mode` and `stretch_mode` *before* the texture and the size, and the orbs drew at double size until it did.
- **A lambda captures by value, and so is a `PackedStringArray`:** anything a test gathers from a signal has to be collected in an `Array`, which is shared, or the count outside the lambda never moves.
- **Nothing on the map changes, so nothing on it is regenerated.** Both map generators are order-dependent, not seed-dependent: `EnvironmentGenerator.extend` seeds its frontier from the order cells were inserted, and `RoadNetwork._route` routes into the roads already laid and abandons a route that would merge illegally. So the same seed and the same final rect do *not* give the same land -- only replaying the identical sequence of windows would, and that would weld every save to one build of the generator. The town world is written down too, though it is a pure function of its seed today, because that is a property of the current code rather than a promise to the player.
- **A tile is named once, and the name is written down.** `MapBuilder._show` names every tile the moment it comes out of the fog and never again, and `MapSave` carries the names rather than regenerating them on load. `TileNames.generate` being a pure function of the map seed and the cell is a property of today's tables, not a promise to the player -- widening a word list or adding a seventh environment would otherwise rename places somebody has already fought over. The fight's HUD is the one place a name is read, so a rename would be read as a different tile.
- **A save that cannot be honoured stops, and is never written over.** Refusing and then generating a fresh world would destroy the old save on the first arrival, which is the one outcome worse than an error message -- the same reason `Inventory` leaves a newer-version file alone. Only a *missing* file means a new world, which is why `MapSave.load_from` has two different nulls.
- **A seed written into the scene wins over a save of another world.** 0 means "carry on"; non-zero means "that world, now", and so does a changed `map_origin`. It is a developer knob, which is why every test and screenshot script redirects `map_path` -- they all pin a seed, so without it they would replace the player's own map.
- **Commit** `.uid` and `.import` files.
