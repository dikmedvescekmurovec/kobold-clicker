## Map code (`Scenes/Map/`)
| File | Contents |
|---|---|
| `hex_grid.gd` (`HexGrid`) | Pointy-top offset grid with odd rows shifted right (same as the TileMapLayers). `Edge` enum (E, SE, SW, W, NW, NE) and `EDGES`, `neighbor`, `neighbors`, `opposite`, `distance`, `corners`, and the edge bitmask pair `edge_mask` / `mask_edges` that roads are described with |
| `sheet_meta.gd` (`SheetMeta`) | Reads `AI-sprites/spritesheet/hex_tileset.json` once per run and hands out its `meta` block, so nothing restates the rules the sprites were drawn to. `env_adjacency()` is the adjacency table, with each environment's self-entry stripped |
| `hex_tileset.gd` (`HexTileset`) | Builds the TileSet at runtime from `AI-sprites/spritesheet/hex_tileset.json` (56×64 tiles). `atlas_coords`, `road_name`, `blend_name`, `env_rank`, `can_border`, `opaque_mask` |
| `hex_map.tscn` / `hex_map.gd` (`HexMap`) | GroundLayer, one `Blend_<env>` layer per spreading environment (created in `_ready`), RoadLayer, Highlight. `set_ground` redraws the blends of the cell and its neighbors, reading the environment of cells that aren't drawn yet through the `hidden_env` Callable, so a tile looks the same however late it is charted. `get_tile_info` includes `blends` and `environments` (visible pixel share per environment). Owns the `fog` overlay and the `player` token. Signals `tile_hovered`, `tile_clicked`, and `dragged` (mouse movement while dragging, for the owner of the camera). A click selects a tile; a press that travels more than `DRAG_THRESHOLD` pans instead. `set_player_cell` moves the player token |
| `player_token.gd` (`PlayerToken`) | The player's character, an `AnimatedSprite2D` with an "idle" and a "run" animation from `Assets/Player`. The sheets' frames are wide (room for the attack swing), so one `BOUNDS` crop, the union over both sheets, cuts every frame down to the character; sharing it keeps the character still when the animation changes. Drawn at `SCALE` (half size). `walk(path)` runs it from tile to tile at `SECONDS_PER_TILE`, `advance(delta)` steps that on (tests drive it directly), `finish_walk()` jumps to the end, and `arrived` fires on the last tile. Kicks up dust every `DUST_EVERY` while walking, from `_process` so tests driving `advance` make none. `HexMap` creates it in code, after the highlight, so it draws on top |
| `fog_overlay.gd` (`FogOverlay`) | The translucent grey hex drawn over every tile that is seen but not charted. A removed cell lifts over `LIFT_TIME` (`_lifting`, drawn only -- `has_cell` is false at once). `HexMap` creates it in code, between the roads and the outlines |
| `ambient.gd` (`Ambient`) | Weather and time of day over the map, added under `HexMap` by the main scene so it hides with it during a fight. One sparse world-space `CPUParticles2D` following the camera, retuned per environment from `WEATHER` on arrival (`set_env`) -- kept to a handful of particles on purpose -- and a `CanvasModulate` cycling to `NIGHT` over `DAY_LENGTH` -- it tints only the map's canvas, never a `CanvasLayer` |
| `hex_highlight.gd` | Hover and selection outlines: a bright band with a dark ink border, readable on every terrain |
| `environment_generator.gd` (`EnvironmentGenerator`) | Random-frontier growth under `ALLOWED`: prefers neighbors, boosts regions under `MIN_REGION_SIZE`, damps regions over `MAX_REGION_SIZE`, then merges small regions. `extend()` grows an existing map into new cells without touching the old ones (they are frozen against merging), which is how the map enlarges. Tunables are at the top |
| `town_world.gd` (`TownWorld`) | 256×256 world of towns (small 1%, medium 0.5%, fortress 0.1%, never on neighboring spots). Each town links to its 1/2/4 nearest towns (small/medium/fortress) within 20 steps, in both directions. `to_dict`/`from_dict` are the map save's copy of the whole world -- towns as flat `[x, y, tier]` against a legend of tier **names**, links once per pair with the lower spot first, and `_buckets` rebuilt rather than stored. It is written down rather than regenerated because "a pure function of its seed" is a property of this code today and not a promise to the player |
| `road_network.gd` (`RoadNetwork`) | Routes roads along the town links with A*, using only shapes the sprites have (straight, 120° curve, 3/4/6-way). Roads stop at town edges and never cross a town tile. Terrain-independent, so a world always gives the same roads. `extend()` adds the links a window brings into reach, routing each inside its own box (around its two towns), so a road never moves once laid — growing the map only ever adds edges, sometimes turning a drawn road into a junction |
| `map_builder.gd` (`MapBuilder`) | Generates the map (the hexagon of `land_radius` round cell (0, 0), which the camera centers on screen, its ice wall and `WASTE_DEPTH` rings of wasteland -- see **The ice wall** below) and draws it as the player uncovers it. `rect` is what the map has generated: it grows only when the wall falls (`_break_wall` -> `_cover`), generating the new land, its tiles and the roads it brings into reach, and redrawing the blends and roads of drawn tiles the new land touches. Everything already generated stays exactly as it is. Every cell is in one `State`: `HIDDEN` (the fog of war, nothing drawn), `UNCHARTED` (drawn under the grey fog, can't be walked to) or `CHARTED`. `create()` generates everything and draws `start_cells()`: the charted center, where the player starts, ringed by six uncharted tiles. `chart(cell, sight := 1)` takes the grey off a tile next to any charted one (`can_chart`; `chart_from` is the charted neighbour the player is fewest steps from), draws the land within `sight` steps of it as uncharted, and sends the player walking onto it. One ring is what a player carrying nothing sees; a torch is the only thing that widens it, and it is read once, by the caller, at the moment the tile is taken — so what a tile showed when it was charted is what it showed, whatever is worn afterwards. Both it and `scour` go through `_reveal_around`, there being one answer to "take the fog off everything within n steps that the map has generated and the player has not seen". `name_of(cell)` is what the tile is called: `_show` names it the first time the player lays eyes on it -- uncharted land is land they can see, so seeing it is the encounter -- and the name is kept in `_names` and written into the save. It is stored rather than worked out again even though `TileNames.generate` is a pure function of the seed and the cell, for the reason the town world is written down: a place somebody has fought over must not be renamed by a later build widening a word list. `level_of(cell)` is the tile's level, in bands that widen as they go (band `n` is `n` tiles wide, so level `n` starts at the nth triangular number) -- what the side panel shows and the ceiling on what can drop there. `area_variant(cell)` says which battle backdrop the tile fights on -- its town tier if it has one, else `road` where a road runs, else `plain`. `can_farm(cell)` is any charted tile with no walk under way -- farming asks nothing about where the player stands, because a run is a thing you choose to do rather than a step you take. `move_to(cell)` sends the player walking to a charted tile over `route_to(cell)`, a shortest path of charted tiles (`can_move_to` refuses anything else, and anything at all while `walking`); arriving emits `arrived(cell)` and charts nothing by itself. `reveal_all()` charts the lot. `origin` is the world spot at cell (0, 0): generated environments, plus that environment's town sprite where the world has a town. Before drawing, it clears any town within `START_TOWN_DISTANCE` (5) of the center and guarantees a small town exactly that far out, which a road links to cell (0, 0); that town's world spot is `start_town`. `_spot(cell)` is the crossing from map cells to world spots. `to_save()` and `restore()` are the map save's two ends: `restore` is the mirror of `create` and shorter than it, because the saved town world already has the clearing and the start town in it and the start road is among the saved roads, so it generates nothing and touches no town. It draws through `_draw_saved`, which lays every ground and road down first and refreshes each cell's blends once, rather than through `_show` -- `set_ground` refreshes a cell **and its six neighbours**, which is seven times the work when a whole map arrives at once |
| `tile_names.gd` (`TileNames`) | What a tile is called: a made-up proper word (a head syllable and a tail one, five hundred pairs) and a feature word taken from the environment, or from the settlement's tier where there is one -- "Bralmere Keep" says more about a fortress than "Bralmere Meadow" does. `generate` is a pure function of the map seed and the cell, under its own `"name"` tag, so what a place is called has nothing to do with which sprite it is drawn with or which backdrop it fights on. It names neither `MapBuilder` nor `TownWorld` -- the caller passes the environment and the tier's name -- so it is a table and a dice roll and nothing else |
| `map_save.gd` (`MapSave`) | The explored map at `user://map.json`: the seeds, the origin, the window, the whole town world, the land, the roads, the names of the tiles the player has seen, and what they have uncovered and where they stand. Version 2 added the names, written out as a plain `"x,y"` object rather than as rows against a legend -- a name is a whole word per cell and only the cells that have been looked at have one, so there is nothing for the alphabet to index; a version 1 save simply has none and its tiles are named again as they are asked about. `_tiles` and the fog are left out, being derived. The environments and the states are **one string per map row, one character per cell**, each indexing a legend written beside it -- which keeps the save small, keeps enum positions off the disk, and makes the env rows read as a picture of the map. `fingerprint(tileset)` is the SHA-256 of the three spritesheet tables a saved map is *read through* (`env_adjacency`, `blend_priority`, `legal_road_masks`) and nothing else, so a rebuilt sheet that only adds a variant costs nobody their map. `load_from` returns **two different nulls**: an empty `problem` is a first run, and a reason in it is a refusal. Never names `MapBuilder` -- that is the cycle Godot's checker bites on, so the states are raw ints here and `STATE_NAMES` is the legend |

**The ice wall.** The land is a hexagon of radius 10 round cell (0, 0), and ring 11 is a wall of ice the player has to fight through: one body (`Encounter.for_wall`), far tougher than anything its ring would field, so it is a wall in both senses -- the edge of the map and the edge of what the player can do yet. Beating any one tile of it brings the **whole ring** down: the land reaches 20, and a new wall stands at 21 (then 31, ...). One gate per tier, like a stage boss, rather than a gap through one tile, because a hole would leave the rest of the ring as scenery and make the next stretch a corridor. Past the wall is a frozen wasteland: the player can see it (sight, torches and scours reveal it like any land), but it is snow with nothing under it, so the land beyond cannot be read, farmed, posted as a bounty or hold a chest before it is earned. The land out there is generated all the same (`WASTE_DEPTH` rings), for two reasons: the wall's own tiles blend against what is really beyond, so nothing on screen changes when it thaws, and sight cannot outrun generated land. The wall replaced edge-growth (`expand_if_needed`, the 20x11 `START_RECT` growing by 10x5 near an edge): the map now grows only when the wall falls. Saves from before the wall (version 2 and older, no `land_radius`) are **migrated rather than refused**: the wall goes on the first ring, counted the way walls fall (11, 21, 31...), past the farthest tile the player has seen, so nothing they had found is iced over. The ice and the snow are a stand-in drawn in the sprite palette's ice ramp (`IceOverlay`) until the generator has art for them. The wall's body in the fight is its own still picture (`Assets/Enemies/The Wall`). **How hard it is** is `Encounter.WALL_HP`, 50: the first wall is meant to fall on the first day, but only after a lot of farming. At the 6 it shipped with it fell in about 350 kills and 13 minutes, in common gear, the moment the Power tree reached Giant Slayer -- the wall is a boss -- so it checked a level and no gear. `tests/balance_wall.gd` plays a fresh player out to it: at 50 about 2100 kills and 50 minutes of fighting at five clicks a second, as a ceiling (that player ignores Fortune, orbs, vendors, the smith and uniques). The dial is a cliff past that (60 is 7000 kills, 100 is 30000), because the Power tree is full at level 24 and drops top out at the farmed tile's level, leaving rarity as the only thing still growing. Turned down: a wall Giant Slayer does nothing to, which plays out exactly as twice the figure and costs a special case; and damage that stays on the wall between attempts, which would flatten the cliff but make it a check on time rather than power -- the thing to reach for if 50 plays as a brick. **Played, 50 felt twice too strong** (2026-09-19), so it is 33: about 850 kills and 25 minutes at five clicks a second, half the time. There is a cliff right behind it -- 34 is already 1600 kills and 36 minutes, 25 to 32 all sit near 550 -- so move it a point at a time and rerun the table. **Every wall fallen multiplies the next by `WALL_GROWTH`, 10:** the second wall is meant to be near impossible without transcending (not built yet), and on the dial alone it was not -- the played-out player held ring 20 inside two hours and had it down to 5 clicks a second after 60000 kills, or about 5000 with a Berserker's Band, a home piece and the Glass Edge on, their damage summing to five times. At 10 that same stack still wants about 15 clicks a second after twenty hours, and a transcend need only be worth five to ten times the player to open it. Turned down: 30, which asks a first transcend for thirty times or the wall never falls.

**Treasure chests.** `MapBuilder.has_chest(cell)` is a per-cell roll (`CHEST_CHANCE`, open land only, `CHEST_MIN_DISTANCE` from the start) that holds until the tile is charted -- derived, not saved, since a won tile is charted. `_draw_chest` puts a sprite (`CHEST_TEXTURE`/`CHEST_REGION`) on a seen chest tile under `HexMap.chests`, over the fog. `nearest_chest()` scans every generated cell, so the main scene calls it on arrival and keeps the answer; hands it to `ChestPointer.target` (`chest_pointer.gd`), a twinkling `Polygon2D` star (not the chest) that pins itself to the window's edge in that direction.

## Rules and gotchas
- **Rules come from the JSON meta:** `blend_rule`, `blend_priority` and `env_adjacency`, all read through `SheetMeta` — `HexTileset.can_border` and `EnvironmentGenerator.allowed()` are the same table, so the generator cannot produce a border the sprites can't draw.
- **Map origins must be on even rows**, otherwise world neighbors don't match on-screen neighbors (`MapBuilder` asserts this).
- **Nothing on the map changes, so nothing on it is regenerated.** Both map generators are order-dependent, not seed-dependent: `EnvironmentGenerator.extend` seeds its frontier from the order cells were inserted, and `RoadNetwork._route` routes into the roads already laid and abandons a route that would merge illegally. So the same seed and the same final rect do *not* give the same land -- only replaying the identical sequence of windows would, and that would weld every save to one build of the generator. The town world is written down too, though it is a pure function of its seed today, because that is a property of the current code rather than a promise to the player.
- **A tile is named once, and the name is written down.** `MapBuilder._show` names every tile the moment it comes out of the fog and never again, and `MapSave` carries the names rather than regenerating them on load. `TileNames.generate` being a pure function of the map seed and the cell is a property of today's tables, not a promise to the player -- widening a word list or adding a seventh environment would otherwise rename places somebody has already fought over. The fight's HUD is the one place a name is read, so a rename would be read as a different tile.
- **A save that cannot be honoured stops, and is never written over.** Refusing and then generating a fresh world would destroy the old save on the first arrival, which is the one outcome worse than an error message -- the same reason `Inventory` leaves a newer-version file alone. Only a *missing* file means a new world, which is why `MapSave.load_from` has two different nulls.
