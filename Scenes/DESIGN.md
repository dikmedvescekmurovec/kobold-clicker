# Main scene (`Scenes/main_scene.gd`) and rules that span several folders

`Scenes/main_scene.gd` has the exported `world_seed` and `map_seed` (0 = carry on from the save, else random; the used seeds are printed), `map_origin`, `zoom` (3 by default, whole numbers only so sprite pixels stay square) and `ui_scale` (2). It prints the clicked tile's environment weights and town connections, and builds the UI in code, so the scene file stays untouched while the editor has it open. **The left-hand pages are their own classes** -- `BagPage` (bag, character sheet, orb tray), `SkillsPage` and the four that came after them, in `Scenes/UI/` -- each taking the inventory, the save path and `ui_scale`, saving what it changes itself, and offering `open()`, `layout()` and a `closed` signal; the main scene owns the corner buttons, which page is up, and tells the bag to `refresh()` / `refresh_gold()` / `refresh_orbs()` when a fight moves the inventory. The shared Control builders (`titled_panel`, `button`, `icon_button`, `label`, `rule`, `vbox`, `clear`) are statics on `UITheme`. What it looks like: a side panel flush against the right edge, running the full window height and hidden until a tile is selected — a green title bar with the title and an X at its right end, over a cream body holding one row per environment on the tile (a 16 px swatch cut from that environment's own hex-sheet tile, plus its percentage), a "Chart", a "Move here" and a "Farm" button pinned to the bottom, each shown only while it can be pressed — charting works on any tile beside a charted one (the player walks onto the tile itself first, through the nearest charted tile beside it, `_walk_to_fight`, and the fight opens on arrival; won, they stay, lost, they run back to where they set out from, `_retreat_cell`), and "Move here" goes back to any tile already charted (the camera follows until the player arrives), and "Farm" walks the player onto a tile already taken and opens an endless run there, and an X top-right that closes the panel and calls `HexMap.deselect()`. Opposite it, **square brown icon buttons** under the character panel in the top-left corner (`UITheme.icon_button`, `CORNER_GAP`) -- two in a row when this was written, six in a column now (see the end of this file) -- the first a chest and a star, each a mark on the pack's brown face with no words on it. They come and go together (`_show_corner`) because what takes them away is never about one of them. The star opens the **Skills** page: the free points over the two trees side by side, each a `SkillTreeView` with a Reset button under it wearing a coin and the price (disabled when nothing is spent or the purse is short). Clicking a skill spends a point and saves; hovering one puts a `SkillCard` **beside the skill itself**, placed as `ItemCard` is beside a square (it was beside the page once, so as not to cover the tree, and the player asked for it where the item card is: the eye is on the skill, not the page's edge). `SkillsPage.open` redraws it from the inventory, and opening the page calls it, because levels and gold both move while it is shut. The page is height-bound: five rows, the title, the points and both resets have to fit a 648 px window at `ui_scale` 2, which is what `SkillTreeView.GAP_Y` is set by. Both pages stand against the left edge, so they share it: `_close_left_pages` and `_open_left_page` are the one place that knows which pages those are, and opening either puts the other away. The chest opens the bag: the same titled panel against the left edge, holding every item the world has handed over as tan squares straight on the cream body — the pack puts nothing between the two, so neither does this — each ringed in its rarity's colour above common. How full it is and what is in the purse share **one line at the top** -- the two things true of the whole bag rather than of anything in it, read in one glance, which also leaves the foot of the panel to the orb tray, which needs the width. The bag is **sectioned by level, highest first**, and inside a level sorted by rarity and then newest first; how full it is stands over the lot as `n / 40`, in `Palette.RUST` once it is, and the **orb tray is a footer at the very bottom**, after both of the two things that expand to fill the panel's height -- so it stands under whichever of them is up, the grid or an open stat block, and never scrolls out of sight, least of all while a piece is open, which is exactly when it is being used. It is a footer rather than a section because orbs are not sorted, filtered or chosen between, so it wants no heading and no buttons; `BagPage.refresh_orbs` is its own call beside `BagPage.refresh_gold`, because a kill moves one count and nothing else and there are ten or fifteen kills to a fight. **The tray is only ever what the player holds, every owned orb lit, and a press picks the orb up** (`BagPage._armed`). It had two states once -- with a piece open, the orbs that could touch it stayed lit and a press spent one there and then -- and the user did away with that (2026-10-01): an orb pressed with a piece open shuts the piece and is picked up instead, so there is one way to craft, never two. Picked up, its socket goes dark, every square it can do nothing to goes grey, and the next bag square or worn socket pressed is crafted where it lies without being opened -- asked for because rolling five pieces meant opening and shutting five blocks. It stays held while any are left, since the press it saves is the one repeated most, and the greyed grid is what says an orb is in hand; opening a piece, a press on bare panel, the same orb again or Escape puts it down. The result is read off the hover card, which a press normally silences until the cursor leaves the square -- but not a press with an orb held (2026-10-01, the user's "don't hide the tooltip"). **The card is lit from behind in the orb's colour as it does** (`ItemCard.shine`), more the better the orb -- the tray's order, which is the trade-up ladder, with a super orb past them all -- so a press says it landed where the lines it changed are read. It was a dithered light behind the square's sprite first, then under the card's lines; the user's reference (Hearthstone's card back as a pack opens) put it behind the card, coming out past its edges, and smooth rather than pixel art, the same day. **The held orb is the mouse cursor** (the setter on `_armed`, `Input.set_custom_mouse_cursor`), because a dark socket at the foot of the bag is not where the player is looking while they choose a piece; the bag being hidden for any reason puts it down, so an orb can never ride the cursor into a fight. **It works on a vendor's shelf as well** (`TownPage.orb_held`, `craft_held`, `VendorStock.put`): the player gambles their own orb on a piece that is not theirs yet, and since `TownPrices.buy_price` is read off the rarity the vendor asks more for what it becomes -- no cheaper than buying the piece and crafting it in the bag, so it is a convenience and not a loop. The smith is still bag pieces only. `BagPage._on_orb_pressed` applies first and spends second, so an orb that turns out to have nothing to do is never consumed, and because crafting adds nothing to the bag and takes nothing out of it the selection survives: `BagPage.refresh` reopens the same index and the block simply says something new. `BagPage._orb_card` hovers **above** the square rather than beside it, which is the one direction there is room in -- one side of the tray is the screen edge and the other is the character sheet, which is also why it is added to the layer **after** the sheet: it overhangs that page for most of the orbs, and tree order is the whole of what decides which of the two the player sees -- and it carries `UITheme.theme()` itself, because a type variation means nothing to a Control with no themed ancestor. It is a **coin and a number**, not the word: `Coins.icon()` in front of the figure, which reads at the glance a footer is given rather than at the reading it is not. Each section's heading carries **Auto** and **Clear**: Clear throws away what is held at that level, Auto stops any more of it arriving. They are two buttons rather than one because a player who is finished with level 3 from now on has not necessarily finished with the three they are holding. A level with a rule on it and nothing in it keeps its heading, which is the only place the rule can be turned off again, and the rule is said in the heading in a word and a colour rather than left to the toggle's pressed face — the pack presses a button by drawing it a pixel lower, which is right for a press you are watching and far too quiet for a state you are reading off four headings at once. The character sheet is a **separate panel standing outside it**, against its right edge: the pack's own wood page next to its cream one, with the sides swapped so what you carry is on the left and what you wear is on the right, and no title bar of its own because the pack gives the spread one over the other page. It opens, closes and hides with the bag, and it has **two states**, decided by what the bag is showing rather than by anything it remembers itself. With nothing selected it is the doll: the pack's silhouette with the eight sockets laid **over the body they belong to** — helmet on the head, offhand on the shield arm, weapon on the sword arm, body on the chest, boots on the feet, and the jewellery in a row beneath, where a body says nothing about where a ring goes. The sockets are translucent (`ItemRarity.SOCKET_ALPHA`), which is the only thing that makes an overlay work: an opaque square would hide the very part it points at, and the pack washes its own sockets over its figure for the same reason. An empty ring or amulet socket carries the pack's faint mark for it. `BagPage.DOLL_SOCKETS` is measured off the sprite and placed by hand — no container expresses "over the shield hand" — and `test_inventory` checks no two sockets overlap and none runs off the page. `BagPage.DOLL_SCALE` is set by that layout rather than by taste: head, chest and feet are 17 and 15 sprite pixels apart, so a 40 px square needs at least 2.7 to clear its neighbours, and whole numbers only, for the reason `zoom` is. (That was the pack's 43x46 figure, drawn at 3; the pixellab doll that replaced it on 2026-09-23 is drawn at 1, its sockets three times as far apart in its own pixels.) With a bag item selected the **comparison takes the doll's place**: everything that item would replace, standing beside that item's own block, at `BagPage.WORN_WIDTH` (the bag's own width, so the two columns wrap alike). The socket is exactly the one the Equip button targets and the pieces are `Equipment.displaced_by`'s, so the page shows precisely what pressing Equip would take off — one piece ordinarily, two where a two-hander and an offhand want the same hands — and rings and the shield-or-torch offhand are settled without a second rule. The panel's own face changes with the state — the pack's wood page under the doll, its cream one under a stat block, because the darker half of the rarity ramp was picked to be read on white and vanishes into wood — and `BagPage.layout` measures and re-centres it each time, twice, for the reason the tile panel is measured twice. Unequip from the comparison keeps the bag's selection open, finding the piece again by identity because what comes back into the bag moves every index after it; Unequip on an opened socket goes back to the doll as it always did. Clicking a square, or a filled socket, puts that item's stat block in the grid's place — name and rarity in that rarity's colour, then what the piece is worth and what it rolled — with Equip and **Discard** over a Back button, or Unequip over one. The block says what the piece **is** and nothing about what it would replace: the comparison is the worn piece standing whole beside it, and a second one written out as signed numbers under the stats said the same thing twice in two different languages, so a selected piece and an equipped one now read exactly alike wherever either is shown. The lines scroll and the buttons under them do not, so a long piece can never push Equip off the bottom of the window. A worn piece has no Discard of its own — the cap is on the bag alone, so nothing presses the player to destroy what they are wearing — and a full bag greys Unequip rather than destroying something to make room for a piece being looked at. Only ever one of the two is open: they share the space. The squares on the panel at the end of a fight open the same way, in the verdict's place. The grid scrolls by wheel and by dragging it, and never shows a scrollbar; a press that travels is a drag and one that does not is a click, the same rule `HexMap` uses to tell a pan from a tile click. Both buttons and every left-hand page go while a fight is on — a `Control` left in that corner would take the mouse before the fight saw it and quietly eat the player's swings. (Since 2026-10-02 the bag's button stays, and the bag opens over the fight: see "Loot goes straight into the bag" below.) `inventory_path` and `map_path` are exported beside the seeds so tests can point them away from the real saves. The map is written at the end of `_ready` (the world is decided the moment it is generated), on every arrival (the one place the map's own state changes) and in `_exit_tree`; a refused save blocks all three. A save that cannot be honoured -- the map **or the inventory**, which is loaded first -- builds no map and no UI at all and puts up a panel saying so, naming the file (`_refuse_save`); with no UI there is no path to either write.

**First-time tips.** `TIPS` lists the one-time pop-ups (first item, first orb, first level-up, first farm run, first charting fight). `_check_tips` runs after every fight (after its kills are banked) and queues any tip whose `_tip_due` state is now true and whose id is not in `inventory.tips`. `first_farm` and `first_chart` are the exceptions: `_open_fight` checks as the fight opens, because they explain the fight on screen. A tip up over a fight disables the combat scene's processing (its clock, input and tweens) until the last queued tip is closed. They show one at a time, centred, built like the refused-save panel, on the character panel's layer (3) so they stand over a fight's (2). The corner buttons are driven by the same list: `_show_corner` shows the bag only once `first_item` or `first_orb` is seen, and the star only once `level_up` is. A newly shown bag or crown pulses (`_flash`) until it is first pressed, which adds `opened_bag` / `opened_heirlooms` to the same list. The star and the trophy pulse on what is waiting instead (`_pulse`): the star while a skill rank can be bought, the trophy while a unique is new to the log -- found and not yet hovered there, where its square glints until it is.

**Tip copy style.** Match the existing tips: a short, evocative title in title case ("Spoils of Battle", "A Spark of Power"), then two or three plain sentences in the game's voice. First say what just happened, then what to do, naming the button by its picture and its corner ("the chest in the top-left corner"). An upbeat nudge can close it. Keep game-system words out ("pouch", "endless", "autodiscard"), along with dashes and anything Pixellari may not draw.

**Spoken tips (2026-09-26).** The user asked for exposition in a dialogue box: words on the left, the speaker's portrait on the right, drawn as a sketch. Two mockups were shown, the sketch as drawn (a plain cream panel, the name as a heading, the portrait in a tan socket behind a rule) and the game's titled popup with the portrait standing on the cream; the user chose their own sketch. It stands at the window's foot rather than in the middle so the counter being explained stays in view. It rides the tips rather than being a system of its own: shown once, saved in `inventory.tips`, queued behind any other tip, Escape to let it go. The first is the fortuneteller on her tab's first opening, in her own voice rather than the tips' narrator, and it explains only what the page already shows (what the signs are, that a reading doubles each time in this world, that a great spell is once a settlement); like every other line of hers it gives no pointer for free, and it says nothing of the way out, which is `first_heirloom`'s. Later the same day the user ruled that **every tip is said by an NPC or by the player**, the player's portrait on the left and every NPC's on the right, and that **each speaker has a voice of their own**: the fortuneteller tired and dry, the hero ("Adventurer" until he is named) cheerful and ready for anything. What made the first drafts read as machine written, in the user's words "too direct and on the nose": tidy lists of three, a stock opener, every page ending on a punchline, the rule said outright. What the user kept: a line of character with the rule left to leak out, or left to the screen (the prices, the tooltips, a corner button's pulse) altogether. The copy in `TIPS` is theirs, chosen and edited line by line. The same day the user asked for a shade behind it with a click anywhere going on, and for the words to come in quickly but gradually: the first click finishes the page, the second turns it. Her portrait is the NPC pack's enchanter; the pack's blacksmith and alchemist are there for the smith and a vendor.

**Reset.** The settings page's **Reset save** (every build; it was a debug-only button in the bottom-left corner once) asks first, then deletes `inventory_path` and `map_path` and reloads the scene; `_resetting` stops `_exit_tree` from writing the saves back on the way out.

## Rules and gotchas
- **No orb falls before the player's 20th kill (50 until 2026-09-27)** (`OrbTable.FIRST_ORB_KILLS`). `inventory.kills` counts every kill across fights; `_open_fight` hands what is left of it to `Encounter.orbs_after`, and `FightLedger.bank_kills` adds a fight's kills when it ends (or the game closes mid-fight).
- **Orbs follow gold, with one difference: gold is one number and orbs are six.** Every fight puts each orb in the inventory as it lands, exactly as the gold beside it. Nothing can refuse an orb either: the bag's cap has nothing to say about a count, no autodiscard rule filters it, and there is no Discard for it.
- **Gold follows loot, with one difference: nothing can refuse it.** Every fight puts each purse in the purse as it lands, exactly as its finds go in the bag. But a purse is a number rather than a square, so the bag's cap has nothing to say about it, an autodiscard rule never filters it, and there is no Discard for it -- a run that threw every find away still earned its way. It is also the half that is never written as a word: the coin stands for it in both places it is said, and `_show_coins` throws it out of the body so the one thing that always drops is the one thing that was never drawn.
- **Loot goes straight into the bag, and the bag can be opened over any fight (the user's, 2026-10-02).** Until then a farm run kept its finds, purse, orbs, experience and bodies in a pouch (`FightLedger`) and the loot counter's popup was where a find was read and thrown away mid-run; the bag went away while any fight was on. The user asked for the bag to open during a fight, the loot to go into it on its own, and the bottom right to be only a summary -- and, asked, for every fight, not only runs. So every gain reaches the inventory as it lands, the popup lost its Discard (the verdict kept its own), and the pouch's machinery went: `bank`, `pending_xp`, a pouch-aware `room_left` and the bounty preview. **What stayed of the pouch is its reason for writing late:** a charting fight writes each gain to disk as it lands, because it is over in half a minute and closing the game mid-fight must not cost a find; a run could go an hour, and writing the whole save on every kill of it was what the pouch avoided, so a run still writes once, at `bank_kills` on its way out (or whenever the bag saves). A crash mid-run loses what it always lost. **The pages moved to layer 3** to stand over the fight's 2; the alternative, putting the bag on the character's layer while a fight is up, would have stood it over the item card. The bag and the fight's own panels (the popup, the verdict) are on different layers, so they put each other away instead of fighting over who is on top. **Gear changed mid-fight counts at once**, which needed `arm` to run twice: everything in it starts from the stats except the clock, which now moves by the difference in the gear's seconds -- taking off a Fight Clock piece takes its seconds back, putting one on gives them, and swapping the two never refills the clock.
- **Monsters outgrow gear on purpose.** Health climbs `HP_GROWTH` per *hex step* while gear climbs `LEVEL_GROWTH` per *level*, and levels arrive in bands that widen -- so the gear exponent grows with the square root of the distance and the health exponent with the distance itself. The player is ahead through the early map and falls behind past the middle distance. Since the clock came down to 30 seconds the frontier is past what a **plain** set of commons can beat, and that is the design rather than a regression: reaching it means farming for better rolls. Farming cannot raise the level a tile drops at — that ceiling is the tile's own — so what a long run buys is modifiers. `test_combat._test_a_won_fight` pins all three ends of that: the first ring stays beatable bare-handed, a plain set at the far edge must need **8 clicks a second or more** (it is out of reach), and a farmed set of rares must bring it under 8 and stay over 1 (not a walkover). (Since the ice wall the test pins two rings instead, the last inside the wall and the first past it -- `Scenes/CLAUDE.md` has the current lines.) `HP_GROWTH`, `LEVEL_GROWTH` and `LEVEL_FLAT` are the dials, and `Encounter.SECONDS` is now one too — over a third of a 30-second fight is `WALK_IN` and `DEATH` animation, so shortening those is the other way to give a fight back its time.
- **"A plain set" now has two readings, and the eight-clicks line holds for one of them.** A slot is several kinds in several materials, so the plainest set the ground deals and the best-material set the same level unlocks are two different sets. Measured at the far edge today: the wooden sword set wants **9.2** clicks a second, the same set in the best material the edge's level reaches wants **7.7**; by weapon, in that best material, dagger 10.5, mace 10.8 (its Bleed counted as the free damage it is) and greatsword 3.3 (bought with the offhand it closes, which is also a torch and a ring of sight). Those are measurements taken on the day, not settled design. The line the design states — a plain set is past what a person can click — is true of the wooden set and comes in just under for the best material, and `_test_a_won_fight` pinned the second at "over 7" rather than smoothing it over (today it pins only that the best material wants fewer clicks than the plain one). **The open question is which dial moves, and the user has not answered it:** `LootTable.TIER_POWER` down from 0.20 to 0.10 would put a top-material sword set back over eight, and the greatsword's own factor of 2.2 is the other candidate. Until then the docs say what is measured.
- **The frontier is measured against a median set, not a seeded one.** `_typical_farmed` rolls `FARMED_SETS` (7) farmed sets at the tile's level and hands back the one whose fight wants the middling number of clicks a second. The single seeded set that came before it was fine until a modifier joined the jewellery's pool: the same seed then drew a different stream, the set happened to roll flat damage on both jewels, and the far edge went from wanting clicks to a walkover (0.56/s) without one number in the game changing. Over fifty seeds that edge wants 0.85 to 7.24 clicks a second with a median of 2.83, and the old seed sat below every one of them. A median cannot be moved that way by one lucky draw — the pool would have to move the whole distribution, which is exactly the case where the frontier really has changed and the check should have something to say.
- **The offensive stats, the three finders, the mace's Bleed and the torch's Sight are wired up:** `damage`, `crit_chance`, `crit_damage` and `attack_speed` are read by `Encounter` and decide what a blow is worth, and `bleed` decides what it leaves behind — a share of the blow the body goes on losing while it stands there. `drop_rate` is read by the same `arm()` and handed to `LootTable.roll`, where it lifts the chance a body leaves anything, capped where that chance has always been capped. The other two finders are read there too and are narrower on purpose: `item_rarity` goes to `ItemRarity.roll`, and `gold_find` lifts a purse at the death site rather than inside `gold_of`, which stays what the body is worth. **Drop rate is the broad one, so it reaches all four kinds of loot**: it is *added* to `gold_find` for the purse and to `orb_find` for `OrbTable.roll`, the way two global percents add rather than compound, and neither `gold_of` nor `OrbTable.chance_for` was taught about a second stat — which is what keeps a town's prices, quoted in bodies, exactly where they were. `sight` is the one live stat the fight never sees: `main_scene._sight()` reads it at the moment a won tile is charted and nowhere else, so putting a torch on uncovers nothing and taking one off hides nothing. The boots' `move_speed` is the other: the map token asks the worn set for it as each walk sets off (a Callable the main scene hands it, rather than a figure it would have to be told again at every equip), and +100% crosses a tile in half of `SECONDS_PER_TILE`, the run cycle sped up to match. The capstone skills' effects are not stats: `main_scene` sets `Encounter.effects` from `Skills.effects()` beside `guarantee_elite`, and `_strike` / `_advance_phase` read them; Jackpot and Transmute draw from `loot_rng` / `orb_rng` only while learned, so a player without them rolls exactly as before. Defence is wired up too, and without a health pool: the enemies strike the clock itself, which is still the only way to lose, and armour, dodge, block and time on hit decide how much of each blow it pays (`Scenes/Combat/DESIGN.md`, "The enemies strike the clock"). The attributes are the one thing gear carries that nothing reads.
- **An autodiscarded find is filtered in exactly one place, `CombatScene._on_loot_dropped`, and the fight is what everything downstream believes.** The main scene no longer listens to `Encounter.loot_dropped` at all; a second listener applying the rule a second way is how the counter, the pouch and the bag would come to disagree about what a run found.
- **A comparison is against what the swap takes off, which is one socket's piece unless a two-hander is involved.** `BagPage._show_item` and the character sheet both ask `Equipment.sockets_for(item)[_socket_pick]` and then `Equipment.displaced_by`, so what is shown beside the piece being judged is exactly what pressing Equip would cost. A ring compares against the emptiest finger, which is the one it would actually go on; a greatsword compares against the sword **and** the shield, and a shield held up while a greatsword is worn compares against the whole greatsword — anything less would have the page say "Nothing worn" over a swap that costs two pieces. Each is a whole stat block with its own Unequip, because one Unequip over two blocks would take the wrong piece off. The blocks are the same block a bag item and a worn one get anywhere else. `ItemDetails.fill` still takes an `against` list and `ItemDetails.deltas` still adds it up, tested on its own; nothing in the bag passes one.
- **The character sheet only changes while something is selected.** The doll is the page's resting state and is untouched — same silhouette, same hand-placed sockets, same wood panel, same centring. The one thing it says about itself is that a hand is full: while a two-hander is worn the offhand socket draws that weapon's own icon faded, the way a bare ring socket wears the pack's ring mark, and a press there opens the weapon. An empty square would have read as somewhere left to fill, which is the opposite of what it means, and a socket has to answer for what it draws. The comparison is what is shown *instead of* it for as long as a bag square is open, and closing the square brings the doll straight back.
- **A square in the bag takes no mouse input at all** (`MOUSE_FILTER_IGNORE`): the grid sits in a `ScrollContainer` that has to see every press to tell a drag from a click, and a square that swallowed the press would break every drag that started on one — which is most of them. Which square was clicked is worked out from where the cursor is.
- **A seed written into the scene wins over a save of another world.** 0 means "carry on"; non-zero means "that world, now", and so does a changed `map_origin`. It is a developer knob, which is why every test and screenshot script redirects `map_path` -- they all pin a seed, so without it they would replace the player's own map.
- **Big numbers are doubles and a formatter, not a bignum class.** Health grows 18% a hex step and gold 12%, and as 64-bit ints they overflowed about 250 steps out on a map with no edge. A double runs to 1.8e308, which is some 4,200 steps -- further than anyone walks -- and keeps `+`, `-` and `>=` as plain operators and the save as plain JSON numbers (which Godot reads back as floats anyway, so old saves needed no migration). A mantissa-and-exponent class was turned down: every sum and comparison in thirty files becomes a method call and the fight loop allocates per hit, to lift a ceiling nobody reaches. `BigNumber.format` corrects its exponent after the log rather than trusting it (`log(1000)/log(10)` is 2.999...), and `test_big_number` walks every power of ten to 1e300 to hold it. The coin burst is capped at `Coins.MOST` because the log was only a cap while an int was the ceiling. Modifier values stay ints for the save's sake (`14`, not `14.0`); flat ones pass int64 near item level 370, marked `# ponytail:` in `ModifierTable`.
- **The settings are a static and a file of their own, not a corner of the inventory.** Reset deletes the saves, and a player who muted the game and starts over has not asked for it back; and the things that read them (`Juice`, the fight's view, `ItemDetails`) are asked from places that share no owner to pass them down. `ConfigFile`, and an unreadable one is the defaults: nothing here is worth refusing to start over. `Settings.path` is empty off the player's own save, which is how no test had to be told about them.
- **Animations off thins what is shown and never what is earned.** Gold, finds and orbs already leave the fight by their own signals before anything is thrown; experience did not -- the bar fills when the last gem lands -- so with no gems `_show_xp` hands it over at once. The enemy's flash and squash stay at every level: they are the only sign a click landed. Low keeps one coin and one gem because a body that leaves nothing looks like a body that paid nothing.
- **A detailed modifier line shows its band beside the number it is about (`+14(8-20)% increased Damage`), and no tier.** There is one band a modifier, grown by item level (`ModifierTable.band_for`); a T1/T2 derived from where the roll sits would be a second way of saying the same two numbers. Real tiers are a loot-table change, not a display one.
- **Reset asks in place, at the page's foot.** The bag's question covers the window because the grid under it is full of things to press; the settings page has nothing under Reset, and closing the page is its Cancel.

**The third tree and transcending the trees (2026-09-21).** Power and Fortune held 46 points, full at level 47, and levels have no cap, so every point past that had nowhere to go. **Bursting the trees replaced overranks (the user's design, 2026-09-29).** Filling all three trees glints, shakes and pops them black, and they start again empty -- but, unlike the transcension below, **the burnt trees keep everything they gave**, stats and capstone effects alike, and every rank of the next tree costs one point more (2, then 3...). **Overranks replaced transcending the trees (2026-09-24; themselves replaced above).** Transcending felt bad: it made the player weaker the moment it was pressed, asked for 69 clicks to get back where they were, made the next fill cost double (138 levels), and was no choice -- every tree had to be full, so the same build came back. ## The cloud save (2026-09-30)

The user asked for saves that follow the player across devices and are "verified after every relevant action, so cheating can't occur", with sign-in "simple -- Google, Apple or similar". I set out three levels (a plain cloud save; a cloud save the server checks; a server that runs the game) and said honestly that no level stops cheating outright here -- the rules run on the player's machine and clicks land, so a bot at human speed is a human to any server. **The user chose level 2**, Google and Discord (Apple needs the $99/yr developer programme), signing in optional, the board open only to signed-in players, and a question whenever two devices disagree.

How it works is in `backend/leaderboard/README.md`; what is worth knowing here:

- **The save is the game's own two files, byte for byte.** Nothing about `Inventory` or `MapSave` changed: the cloud moves the files and the server reads only the inventory's summary (level, time played, when saved, floors) out of it, so a new field in the save needs nothing from the cloud.
- **A change of device is a download, not a question, because the first sync after a start-up judges the device by the files as the scene found them** (`Cloud.launched`). Start-up always writes (the map, a camp's pay); judged by the files after that, every change of device was a question. The e2e run found it.
- **The checks are gone (2026-10-02).** The user: "Remove the cloud save check. It's not working. Assume player is not cheating." The server now takes every save at its word: no `consistent` / `follows`, no 422 and no refusal question, and the board takes the save's own `dungeon_floors` (it only ever rises) where it once counted only floors beaten under the checks (`saves.vouched`). The conflict question between two devices stays: it was never a check. The columns `saves.checked` / `saves.vouched` and `players.flag` are left in the database, unread.
- **Level 3 (a server that replays the game) was turned down for now:** the rules are ~9,000 lines of GDScript that would have to run headless on a rented server, fights step on a variable frame delta, loot is deliberately unseeded, and the game would have to be online to be played.
